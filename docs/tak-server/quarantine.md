# 隔離使用者：TAK Server 不能立刻重新啟動時的減災

本頁說明如何在不重新啟動 TAK Server 的情況下，把一位使用者和其他人隔開。使用時機是：某張用戶端憑證疑似外洩或某人必須立刻停止存取，但現場仍在用 TAK，不能中斷所有人的連線。

**隔離不是停權。**它只是爭取時間；事後一定要撤銷憑證並重新啟動 TAK Server。

**目前狀態：**本頁的步驟在 2026-11-14 以 API、模擬用戶端、Android 模擬機與一台實體手機驗證過（檔案模式與 LDAP 模式；兩台裝置都當過被隔離的對象），還沒有做進憑證控制台。任務變更通知已在手機的 Data Sync 外掛上確認。現行部署使用檔案驗證；LDAP 的步驟適用於日後依 [OpenLDAP 導入計畫](../plans/openldap.md)啟用之後。

## 為什麼需要隔離

撤銷憑證要等 TAK Server 重新啟動才生效。在 CA 撤銷並發布 CRL 之後、重新啟動之前：

- 既有連線繼續運作。
- 用已撤銷的憑證建立的新連線也被接受。實測 40 分鐘內 TAK 不會自行重新載入 CRL。
- LDAP 不能拒絕憑證連線；已撤銷的憑證照樣拿到 LDAP 群組。

憑證控制台與憑證工作佇列的撤銷流程都包含重新啟動，會中斷所有人的連線。隔離讓你先把風險關起來，再選時間重新啟動。

## 隔離的效果與限制

做法是把該使用者的群組換成一個**只有他自己的群組**。TAK 依群組分流資料，所以他和其他人互相收不到。

| 項目 | 隔離後 |
| --- | --- |
| 位置等即時事件 | 當下雙向停止 |
| 聊天訊息（私訊與 All Chat Rooms） | 雙向都送不到；傳送端沒有失敗提示，解除隔離後也不補送 |
| 原群組的任務 | 列不出、讀不到、不能重新訂閱 |
| 原群組的檔案 | 以雜湊下載得到 HTTP 404，包含隔離前下載過的檔案 |
| 連線清單與聯絡人 | 只看得到自己 |
| 重新連線 | 仍然落在隔離群組 |
| 目錄斷線（LDAP 模式） | 目錄與檔案兩邊都改過才仍然隔離 |

擋不住的：

| 項目 | 說明 | 處理方式 |
| --- | --- | --- |
| 隔離前訂閱的任務 | 仍然把變更通知推送給他；檔案模式與 LDAP 模式都是。他的 ATAK 下載不到新檔案（HTTP 404），但任務紀錄會顯示「User added <檔名>」，看得到檔名 | 盡早刪除他的任務訂閱（步驟 4） |
| 連線本身 | 他仍連得上 `8089` 與 `8443` | 撤銷後重建輸入埠（步驟 7）、重新啟動（步驟 8） |
| 已下載的資料 | 已經在裝置上的地圖物件、檔案與任務內容收不回來 | 無 |

## 開始之前

- **隔離群組的名稱**要是別人不會用到的名稱，一人一個。本頁以 `quar-<名稱>` 表示檔案內的群組，以 `tak_QUAR_<名稱>` 表示目錄內的群組；目錄內的名稱要符合 `<ldap>` 的 `groupprefix`。
- **不要用「移除所有群組」代替隔離。**無群組的憑證會進入 `__ANON__`，那是一個共用群組：所有無群組的使用者互相可見，也看得到屬於 `__ANON__` 的任務。
- **管理 API 以管理員憑證呼叫 `8443`。**`scripts/tak_api_client.py` 固定連 `.env` 的 `TAK_BIND_IP`；主機沒有該位址時，呼叫會逾時。
- 先記下該使用者的憑證 CN，以及他的用戶端 UID（訂閱清單的 `clientUid`）。

## 步驟

### 1. 把檔案內的群組改成隔離群組

呼叫管理 API（實測使用的方式）：

```text
PUT /Marti/api/user-management/api/update-groups
{"username": "<CN>", "groupList": ["quar-<名稱>"], "groupListIN": [], "groupListOUT": []}
```

讀回確認：

```text
GET /Marti/api/user-management/api/get-groups-for-user/<CN>
```

[用戶端憑證控制台](certificate-console.md)的群組頁也是修改檔案內的群組，但這次沒有用它驗證隔離。

檔案驗證模式下，這一步完成後隔離就生效，既有連線 1 秒內換到新群組。

LDAP 啟用且目錄正常時，這一步**本身沒有作用**，TAK 仍以目錄的群組為準。它的用途是：目錄斷線時 TAK 會退回檔案內的群組，檔案內若還是舊群組，隔離就會失效。實體手機上實測：只改目錄時，目錄停止 45 秒後它回到原群組，隊友重新看得到它；補改檔案後 2 秒內恢復隔離。

### 2. LDAP 模式：把目錄內的群組也改成隔離群組

在目錄內建立只有他一個成員的 `tak_QUAR_<名稱>`，並把他從其他所有 `tak_` 開頭的群組移除。既有連線在 11 到 67 秒內換到新群組（`updateinterval="60"`）。

檔案驗證模式略過這一步。

### 3. 確認群組已經改變

```text
GET /Marti/api/subscriptions/all
```

找到他的連線，確認 `groups` 只剩隔離群組，IN 與 OUT 都是。同時記下這條連線的 `subscriptionUid`（形式是 `tls:<編號>`）與 `clientUid`。

**以訂閱清單為準，不要看 ATAK 的 Contacts。**實測伺服器停止轉送後，雙方畫面上的對方仍維持綠點 3 分鐘以上。需要旁證時，用另一個同群組的用戶端確認收不到他的位置。

### 4. 刪除他的任務訂閱

群組變更不會停止任務的變更通知。對他訂閱的每一個任務：

```text
DELETE /Marti/api/missions/<任務名稱>/subscription?uid=<clientUid>
```

實測刪除後，原任務再有變更時他不再收到通知（模擬用戶端與實體手機，兩種模式）。

刪除後不要用任務的訂閱清單確認：實測呼叫回 HTTP 200、通知也確實停止，但清單仍列出他的用戶端 UID，原因沒有查明。

目前沒有查明如何一次列出某位使用者訂閱的所有任務。可以在隔離**之前**逐一查各任務的訂閱清單（`GET /Marti/api/missions/<任務名稱>/subscriptions`），找出他訂閱了哪些。

### 5. 視需要踢掉他的連線

```text
DELETE /Marti/api/subscriptions/delete/<subscriptionUid>
```

要用 `subscriptionUid`；用 `clientUid` 會得到 HTTP 400。ATAK 會在 15 到 26 秒內自行重連，重連後仍在隔離群組。這一步的用途是讓他的連線重新建立，不是把他擋在外面。

**要讓他連不回來，先做步驟 6 與 7 再踢除：**重建輸入埠只影響新連線，他的既有連線會留著，直到重新連線時才被拒絕。實體手機上實測：撤銷、重建輸入埠之後再踢除，它在 130 秒內重試 9 次全部被拒絕，隊友的連線不受影響。

### 6. 撤銷憑證並發布 CRL

執行 `scripts/revoke_tak_certificate.py`。它在 CA 撤銷並發布 CRL，不會重新啟動 TAK。憑證控制台的撤銷會重新啟動 TAK；不能重新啟動時不要用它。

### 7. 重建 `8089` 的輸入埠

讓 `8089` 重新讀取 CRL，不必重新啟動 TAK：

```text
GET    /Marti/api/inputs                 （記下 stdssl 的完整設定）
DELETE /Marti/api/inputs/stdssl
POST   /Marti/api/inputs                 （送回剛才記下的設定）
```

實測結果：

- 已撤銷的憑證之後在 `8089` 建立新連線會被拒絕。
- 其他人的既有連線沒有中斷，其他憑證可以照常建立新連線。
- 刪除到重建之間約 3 秒，這段時間的新連線會失敗。
- TAK 會把輸入埠寫回 `runtime/tak/CoreConfig.xml`，原本省略的屬性被展開成預設值。功能相同，但檔案內容改變。
- 他的既有連線也不會中斷；重新連線時才被拒絕。被拒絕時 ATAK 只顯示「IO error; reconnecting」，約每 15 秒重試，沒有提到憑證已撤銷。
- **`8443` 不受影響。**他仍然可以用已撤銷的憑證呼叫 API，只是看不到隔離群組以外的資料。

### 8. 可以重新啟動時，重新啟動 TAK Server

重新啟動後，`8089` 與 `8443` 都會拒絕已撤銷的憑證，撤銷才算完成。確認方式見[憑證與撤銷](../security/certificates.md)。

重新啟動後可以清掉隔離群組：檔案內的群組登錄，以及目錄內的 `tak_QUAR_<名稱>` 與他的帳號。

## 解除隔離

若事後確認是誤判、還沒有撤銷憑證，把步驟倒回來：

1. 目錄內把他加回原群組，移出並刪除 `tak_QUAR_<名稱>`。
2. 檔案內的群組改回原值。
3. 用訂閱清單確認群組已回復。
4. 請他在 ATAK 重新訂閱需要的任務；被刪除的訂閱不會自動回復。

憑證一旦撤銷就無法回復，要重新簽發。

## 導入 LDAP 時的設計要求

這些要求來自實測，寫在 [OpenLDAP 導入計畫](../plans/openldap.md)第 6 節：

- 每位受 LDAP 管理的使用者，平時就在檔案內登錄成只有自己的群組。這樣目錄斷線時每個人各自隔開，不會依檔案內的舊資料混組；緊急隔離時也只需要改目錄。代價是目錄斷線期間整隊互相看不到。
- 不要留下「在目錄內、但檔案沒有登錄」的帳號。目錄斷線時，它的既有連線保留原本的 LDAP 群組，新連線卻落入 `__ANON__`。
- 控制台要提供一個「隔離」操作，一次做完步驟 1 到 4 並讀回確認。

目錄端的帳號鎖定幫不上忙：它只擋得住帳號密碼登入，同一個人用憑證連 `8089` 與 `8443` 都照常。

## 驗證範圍

已實測（2026-11-14，TAK Server `5.8-RELEASE-84`；模擬用戶端與管理 API，另以 Android 模擬機與一台實體手機重做）：

- 檔案模式與 LDAP 模式的隔離、目錄斷線與恢復、隔離後重新連線。
- 隔離後的任務、檔案、檔案搜尋、連線清單範圍（檔案模式與 LDAP 模式）；`__ANON__` 的範圍。
- 任務變更通知的殘留，以及刪除訂閱後停止：模擬用戶端與實體手機（Data Sync 外掛），兩種模式。
- 聊天訊息在隔離期間的收發；無群組憑證在 ATAK 上的連線狀態。
- 先撤銷、重建輸入埠，再踢除的順序。
- ATAK 被踢除後的重連時間、被拒絕時的畫面提示、Contacts 畫面的延遲。
- 強制斷線的識別碼、重建輸入埠後 `8089` 拒絕已撤銷的憑證。

未實測：

- 任務內檔案以外的內容（地圖物件、紀錄文字）在隔離後的通知會洩漏什麼。
- 刪除任務訂閱後，清單仍列出該用戶端的原因。
- 被隔離的連線能否用訂閱時取得的權杖讀取任務。
- 一次列出某位使用者所有任務訂閱的做法。
- 裝置設定檔、聯邦在隔離狀態下的範圍。
- 輸入埠上有大量連線時重建的影響；`8443` 不重新啟動就重新載入 CRL 的方式。
