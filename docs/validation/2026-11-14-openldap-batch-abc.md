# 2026-11-14 OpenLDAP 補測批次 A、B、C

## 結論

1. **目錄與檔案都設成隔離群組後，目錄斷線仍然隔離。**斷線期間目標使用者退回檔案內的隔離群組，既有連線與新連線都只看得到自己。
2. **目錄正常時，只改檔案內的群組沒有作用。**隔離一定要改目錄；檔案內的修改是為了目錄斷線時不會退回舊群組。
3. **帳號在目錄內、檔案沒有登錄時，目錄斷線的結果因連線而異。**既有連線保留斷線前的 LDAP 群組（至少 2 分鐘），新連線進入 `__ANON__`，並與其他無群組的使用者互相可見。
4. **平時在檔案內為每人登錄隔離群組的設計可行。**目錄正常時三人同組；斷線後 56 秒內各自退到自己的群組；恢復後 49 秒內回到同組。
5. **兩個無群組的使用者互相可見。**`__ANON__` 是一個真正共用的群組。
6. **`__ANON__` 與被隔離的使用者在 `8443` 拿不到其他群組的任務與檔案**，也不能把任務建到別的群組。
7. **隔離前訂閱的任務，隔離後仍會把變更通知推送給被隔離的連線。**隔離後 6 秒與 97 秒各收到一筆。由管理員刪除他的任務訂閱後，通知停止。隔離流程要加上這一步。
8. **TAK 不會自行重新載入 CRL。**撤銷後 40 分鐘內，用已撤銷憑證建立的 9 次新連線全部被接受；重啟後才被拒絕。
9. **強制斷線要用 `subscriptionUid`。**被踢掉的隔離使用者可以立刻重連，重連後仍在隔離群組。

本紀錄執行 [OpenLDAP 補測計畫](../plans/openldap-test-plan.md)的批次 A、B、C，接續[撤銷時機、隔離群組與無群組憑證](2026-11-14-revocation-quarantine-groupless.md)。所有測試憑證都已撤銷，實驗容器、測試任務與測試檔案都已移除，`runtime/tak/CoreConfig.xml` 的 SHA-256 與修改前相同。

## 測試環境

- TAK Server `5.8-RELEASE-84`（hardened），Windows Docker Desktop，`tak-server` 以 `127.0.0.1` 發布 `8089`／`8443`。
- 批次 A：官方 `takserver-ldap-5.8-RELEASE-92` 容器、唯讀服務帳號、`ldaps://`、`updateinterval="60"`，設定同[第 0 階段](2026-11-14-openldap-phase0.md)。
- 批次 B、C：檔案驗證（LDAP 關閉）。
- 測試憑證：憑證工作佇列簽發的一日效期憑證，每輪使用新的 CN 前綴。
- 模擬用戶端：Python TLS CoT 用戶端，在 `tak-edge` 網路內的容器執行，每 2 秒送一筆 SA 事件，記錄每個 UID 第一次與最後一次收到的時間，以及非 SA 事件的類型。
- 群組讀取：以管理員憑證輪詢 `GET /Marti/api/subscriptions/all`。API 權限測試以各測試憑證直接呼叫 `8443`。
- 沒有使用 Android 模擬機或實體裝置。

本紀錄不含密碼、實際位址、憑證序號或裝置識別資訊。

## 批次 A：隔離與目錄斷線

### 設定

| 使用者 | 目錄內的群組 | 檔案內的群組 |
| --- | --- | --- |
| 目標使用者 | `tak_ALPHA`，之後移到 `tak_QUAR_bad` | 原群組，之後改成隔離群組 |
| 隊友 | `tak_ALPHA` | 原群組 |
| 無檔案登錄者 | `tak_ALPHA` | 沒有登錄（簽發後從 `UserAuthenticationFile.xml` 移除並重啟） |
| 使用者 1–3 | `tak_ALPHA` | 各自只有一個隔離群組 |
| 無群組者 | 不在目錄內 | 群組清空 |

每位使用者有一條長時間連線；五個時間點各另開一批新連線。

### 各時間點的群組

| 時間點 | 目標使用者 | 隊友 | 無檔案登錄者 | 使用者 1–3 |
| --- | --- | --- | --- | --- |
| 1. 目錄正常 | `tak_ALPHA` | `tak_ALPHA` | `tak_ALPHA` | `tak_ALPHA` |
| 2. 只把檔案改成隔離群組 | `tak_ALPHA`，沒有變 | `tak_ALPHA` | `tak_ALPHA` | `tak_ALPHA` |
| 3. 目錄內移到隔離群組 | 22 秒後 `tak_QUAR_bad` | `tak_ALPHA` | `tak_ALPHA` | `tak_ALPHA` |
| 4. 目錄斷線 2 分鐘 | 檔案內的隔離群組 | 檔案內的原群組 | 既有連線 `tak_ALPHA`；新連線 `__ANON__` | 各自的檔案隔離群組 |
| 5. 目錄恢復 | `tak_QUAR_bad` | `tak_ALPHA` | `tak_ALPHA` | `tak_ALPHA` |

時間點 1 與 2，`tak_ALPHA` 的六位成員互相收到事件；時間點 2 目標使用者仍與所有人互相可見，證實目錄正常時檔案內的群組被忽略。

時間點 3 之後，目標使用者只收到自己的事件，其他人也收不到他。

時間點 4（停止 LDAP 容器後 30 秒內群組未變，56 秒時已全部退回檔案群組）：

- 目標使用者的既有連線與新連線都在檔案內的隔離群組，只收到自己。**A1 通過。**
- 使用者 1 的新連線只收到自己的長時間連線，收不到使用者 2、3。**A3 通過。**
- 無檔案登錄者的既有連線在訂閱清單上一直是 `tak_ALPHA`；但其他成員都已退回檔案群組，所以它實際上收不到任何人。
- 無檔案登錄者的新連線是 `__ANON__`，與無群組者互相收到事件。

時間點 5：重新啟動 LDAP 容器後，目標使用者 45 秒回到 `tak_QUAR_bad`，其他人 49 秒回到 `tak_ALPHA`。

### 對設計的含意

- 「每人在檔案內登錄隔離群組」不是隔離生效的必要條件，但它讓斷線時的行為一致，且避免新連線落入共用的 `__ANON__`。代價是斷線期間整隊互相不可見。
- 沒有檔案登錄的帳號在斷線時行為不一致：既有連線與新連線的群組不同。導入時不建議留下這種帳號。
- 既有連線保留 LDAP 群組只觀察了 2 分鐘，沒有測更長的斷線。

## 批次 B：`__ANON__` 與隔離狀態的資料範圍

以管理員憑證建立三個任務，分屬 `__ANON__`、原群組與隔離群組；另上傳三個小檔案，一個由無群組使用者上傳，兩個由原群組的隊友上傳。

### B1：兩個無群組使用者

兩張憑證在檔案內群組清空後同時連線，訂閱清單顯示兩者都是 `__ANON__` IN＋OUT。雙方互相收到對方的 SA 事件；其中一方呼叫 `/Marti/api/contacts/all` 得到兩筆，包含對方。

### B2、B5：`__ANON__` 使用者在 `8443`

| 項目 | 結果 |
| --- | --- |
| 列出任務 | 只有屬於 `__ANON__` 的任務 |
| 讀取原群組、隔離群組的任務 | HTTP 404 |
| 以雜湊下載自己上傳的檔案 | HTTP 200 |
| 以雜湊下載原群組的檔案 | HTTP 404 |
| 建立任務並指定原群組（B5） | HTTP 403，訊息指出不得設定任務的群組；原群組成員的任務清單沒有變化 |
| 檔案搜尋（`/Marti/sync/search`） | 補測：回傳 4 筆，其中測試檔只有自己上傳的那一個；原群組的 4 個測試檔都不在結果內。原群組的隊友則搜得到那 4 個 |

裝置設定檔沒有準備，未測。

### B3：被隔離的使用者在 `8443`

目標使用者先在原群組列出任務、訂閱任務並下載一個檔案，都成功。之後以管理 API 把檔案內的群組改成隔離群組；訂閱清單在同一秒顯示新群組。隔離後 20 秒：

| 項目 | 結果 |
| --- | --- |
| 列出任務 | 只有隔離群組的任務 |
| 讀取原任務 | HTTP 404 |
| 以雜湊下載原群組的兩個檔案（含隔離前下載過的） | HTTP 404 |
| 重新訂閱原任務 | HTTP 404 |
| 管理員列出原任務的訂閱 | 仍有 2 筆，目標使用者的訂閱紀錄沒有被移除 |

### B4：隔離前的任務訂閱

第一輪的結果無法判定，原因見「測試過程的問題」。修正模擬用戶端後補測一輪，記錄每一筆任務變更通知（`t-x-m-c`）的時間：

| 時間（相對於隔離） | 事件 | 目標使用者的既有連線 |
| --- | --- | --- |
| －21 秒 | 隊友在原任務新增內容（對照組） | 收到通知 |
| －1 秒 | — | 最後一次收到隊友的 SA 事件；隊友也最後一次收到他的 |
| 0 秒 | 隔離；1 秒後訂閱清單顯示隔離群組 | — |
| ＋5 秒 | 隊友新增第二筆內容 | ＋6 秒收到通知 |
| ＋96 秒 | 隊友新增第三筆內容 | ＋97 秒收到通知 |
| ＋127 秒 | 管理員刪除目標使用者的任務訂閱（`DELETE /Marti/api/missions/{name}/subscription?uid=<用戶端 UID>`，HTTP 200） | — |
| ＋139 秒 | 隊友新增第四筆內容 | 之後 2 分鐘沒有收到通知 |

結論：

- **SA 事件在隔離當下就停止**，雙向都是。
- **任務變更通知不受群組變更影響。**只要訂閱還在，被隔離的連線就繼續收到。**B4 不通過。**
- **刪除任務訂閱可以擋住通知。**
- 通知的內容沒有檢查。隔離後以雜湊下載原群組的檔案是 404（B3），所以外洩的是「任務有變更」及通知所帶的中繼資料，不是檔案本身。

### 強制斷線（C3、C4）

`GET /Marti/api/subscriptions/all` 的每筆連線有 `clientUid` 與 `subscriptionUid` 兩個識別欄位。逐一用於 `DELETE /Marti/api/subscriptions/delete/{uid}`：

| 欄位 | 值的形式 | 結果 |
| --- | --- | --- |
| `clientUid` | CoT 事件的 UID | HTTP 400，連線沒有中斷 |
| `subscriptionUid` | `tls:<編號>` | HTTP 200，連線中斷 |

模擬用戶端被踢掉後不會自動重連，所以沒有量到重連時間。

C4：踢掉已隔離的目標使用者後，用同一張憑證建立新連線。連線被接受，訂閱清單顯示隔離群組，20 秒內沒有收到任何隊友的事件；輪詢期間沒有出現原群組。

## 批次 C：CRL 重新載入

### C1：長時間不重啟

以 `scripts/revoke_tak_certificate.py` 撤銷一張憑證並發布 CRL，不重啟 TAK；確認序號在掛載給 TAK 的 CRL 檔內。之後每 5 分鐘用這張憑證建立一次新連線。

| 時間點 | 結果 |
| --- | --- |
| 撤銷後 0、5、10、15、20、25、30、35、40 分鐘 | 9 次都被接受；前 4 次同時有隊友在線，隊友收到它的事件，訂閱清單顯示原群組 |
| 重啟 TAK 後 | `SSLV3_ALERT_CERTIFICATE_REVOKED` |

40 分鐘內 TAK 沒有自行重新載入 CRL。更長的時間沒有測。

### C2：不重啟的重新載入方式

沒有實測。靜態分析只找到一條線索：TAK 內部有重新整理 TLS 設定的函式，但只被聯邦相關的元件呼叫，設定指南也沒有記載任何不重啟就重新載入 CRL 的做法。管理介面的 Manage Security 頁面沒有試。

## 對維運的影響

- **隔離之後要刪除該使用者的任務訂閱。**群組變更會立刻停止位置與聊天等事件，但他訂閱過的任務仍會推送變更通知。要逐一對他訂閱的任務呼叫刪除訂閱的 API。
- **隔離一定要改目錄。**LDAP 啟用且目錄正常時，只改檔案沒有作用。檔案內的修改是為了目錄斷線。
- **隔離之後可以再踢掉連線**（`subscriptionUid`），讓對方的連線重新建立在隔離群組上。這不是停權：他可以立刻重連。
- **撤銷之後一定要重啟 TAK。**等待不會讓 CRL 生效。
- **不要留下「在目錄內、但檔案沒有登錄」的帳號。**目錄斷線時它的新連線會落入 `__ANON__`。
- **`__ANON__` 是共用群組。**任何無群組的憑證都會互相看到，也看得到屬於 `__ANON__` 的任務。

## 測試過程的問題

- 批次 A 第一輪的輔助程式有一個函式名稱與 Python 的 `http` 模組相同，所有修改群組的管理 API 呼叫都失敗。該輪只有 A2 的觀察有效；A1、A3 以修正後的程式重跑，本紀錄的批次 A 數字來自重跑。兩輪的 A2 結果一致。
- 第一輪檔案搜尋的回應在紀錄內被截斷，無法事後判定內容；補測時改為比對雜湊。
- `DELETE /Marti/sync/delete` 以管理員憑證呼叫得到 HTTP 403。加進任務的兩個測試檔隨任務的 deepDelete 移除；剩下的一個改用 `DELETE /Marti/api/files/{hash}` 刪除。
- 第一輪的模擬用戶端會把接收緩衝區內的舊事件重複記上新的時間，「最後一次收到」因此偏晚。第一輪看起來像是隔離後資料還多流了 10 到 25 秒，那是量測假象；B4 也因此無法判定。修正為逐筆事件處理後補測，本紀錄 B4 的數字來自補測。批次 A 與 B1 的結論不受影響，但其中「最後一次收到」的時間可能偏晚數秒。
- 各輪的模擬用戶端仍收到少數來源不明的 UID。這次記錄了非 SA 事件的類型：`t-x-takp-v`（TAK 的協定版本訊息）與 `t-x-d-d`（用戶端離線通知）。UID 的來源仍未逐筆核對。

## 未測試

- 任務變更通知的內容，以及被隔離的連線能否用訂閱時拿到的權杖讀取任務。
- 找出某位使用者訂閱了哪些任務的做法；補測只處理單一已知任務。
- 裝置設定檔在 `__ANON__` 與隔離狀態下的範圍。
- 目錄斷線超過 2 分鐘時，無檔案登錄者的既有連線是否仍保留 LDAP 群組。
- 批次 B、C 在 LDAP 模式下的行為；這兩批只在檔案模式執行。
- 不重啟就重新載入 CRL 的方式（C2）。
- ATAK 被強制斷線後多久重連；本批沒有使用模擬機或實體裝置。
