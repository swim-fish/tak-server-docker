# 2026-11-14 OpenLDAP 補測 C2 與批次 D、E

## 結論

1. **不重啟 TAK 也能讓 `8089` 重新載入 CRL。**經管理 API 刪除再重建 TLS 輸入埠後，已撤銷的憑證立刻被拒絕；既有連線沒有中斷，其他憑證照常連線。
2. **這個做法管不到 `8443`。**重建輸入埠後，已撤銷的憑證仍可呼叫 `8443` 的 API，要等 TAK 重啟。
3. **官方 LDAP 套件依導入計畫調整後可以運作。**`slapd` 以非 root 執行、憑證目錄唯讀掛載、服務帳號不受密碼到期影響、收緊 ACL、稽核紀錄保存、匯出與還原都通過。
4. **兩層 CA 簽發的 LDAP 憑證可用，TAK 的信任憑證庫只需要根 CA。**這是以實驗用 CA 模擬本專案 PKI 的結構；沒有用本專案的 CA 實際簽發。
5. **信任憑證庫不含正確 CA 時，TAK 不會報錯，而是所有人靜默退回檔案群組。**健康檢查仍然正常。
6. **LDAP 管理介面需要可寫入的服務帳號。**`isLdapTakComplient` 的檢查是實際建立並刪除一筆測試使用者；唯讀帳號回 `false`，可寫入帳號回 `true`。
7. **帳號密碼登入可以被目錄端擋下。**鎖定帳號後，`8446` 的新登入與 `auth="ldap"` 輸入埠的新連線都被拒絕；既有的 `auth="ldap"` 連線在 45 秒內被伺服器中斷。
8. **鎖定帳號對憑證連線沒有作用。**同一個使用者以憑證連 `8089` 與 `8443` 都照常，也照常拿到 LDAP 群組。
9. **已簽發的登入權杖不受鎖定影響。**權杖效期 130 分鐘；鎖定後 140 秒仍可使用，之後沒有再測。
10. **套件預設的密碼政策會讓任何人鎖住別人的帳號。**連續 5 次錯誤密碼後，帳號鎖定 15 分鐘。

本紀錄執行 [OpenLDAP 補測計畫](../plans/openldap-test-plan.md)的 C2、批次 D 與批次 E，接續[補測批次 A、B、C](2026-11-14-openldap-batch-abc.md)。所有測試憑證都已撤銷，實驗容器、volume、映像與信任憑證庫都已移除，`runtime/tak/CoreConfig.xml` 的 SHA-256 與修改前相同。

## 測試環境

- TAK Server `5.8-RELEASE-84`（hardened），Windows Docker Desktop，`tak-server` 以 `127.0.0.1` 發布 `8089`／`8443`。
- LDAP：官方 `takserver-ldap-5.8-RELEASE-92` 套件建置的容器，以 Compose override 啟動，服務名稱 `tak-ldap`，只接 `tak-backend`。
- 測試憑證：憑證工作佇列簽發的一日效期憑證。
- 模擬用戶端：在 `tak-edge` 網路內的容器執行。`8446` 與 `8090` 沒有發布到主機，只從容器網路內測試。
- 沒有使用 Android 模擬機、實體裝置或瀏覽器。

本紀錄不含密碼、實際位址、憑證序號或裝置識別資訊。

## C2：不重啟 TAK 重新載入 CRL

### 靜態分析

反組譯 TAK 的類別後確認：

- 每個輸入埠在建立時各自產生一份 TLS 設定，並在那時讀取 `<crl>` 指定的檔案。之後不會再讀。
- TAK 內部另有一個重新整理 TLS 設定的函式，但只有聯邦相關的元件會呼叫，用戶端輸入埠不經過它。

所以推論：重新建立輸入埠就會重新讀取 CRL。

### 實測

| 步驟 | `8089` 以已撤銷憑證建立新連線 | `8443` 以已撤銷憑證呼叫 API |
| --- | --- | --- |
| 撤銷前 | 接受 | HTTP 200 |
| 撤銷並發布 CRL，TAK 未重啟 | 接受 | HTTP 200 |
| `DELETE /Marti/api/inputs/stdssl`，再以原設定 `POST /Marti/api/inputs` | `SSLV3_ALERT_CERTIFICATE_REVOKED` | HTTP 200 |
| 重啟 TAK | `SSLV3_ALERT_CERTIFICATE_REVOKED` | 未測 |

其他觀察：

- 容器的啟動時間沒有變，TAK 確實沒有重啟。
- 一條未撤銷憑證的既有連線在刪除與重建輸入埠期間沒有中斷，重建後仍收到新連線的事件。
- 未撤銷的憑證在重建後可以建立新連線。
- TAK 會把重建的輸入埠寫回 `CoreConfig.xml`，原本省略的屬性被展開成預設值。功能相同，但檔案內容改變；實驗後以備份還原。

### 限制

- 只測了一次，輸入埠從刪除到重建約 3 秒。這段時間內的新連線會失敗，沒有測量影響。
- `8443` 的連接器沒有對應的 API。已撤銷的憑證在 TAK 重啟前仍可讀取任務與檔案。
- 沒有測輸入埠上有大量連線時的行為。

## 批次 D：官方套件的調整

### 設定

Compose override 與導入計畫第 5 節相同，另加 `command: ["-u", "openldap", "-g", "openldap"]`。憑證以實驗用的兩層 CA 簽發：`root-ca.pem` 內含根 CA 與中繼 CA，`server.crt` 內含伺服器憑證與中繼 CA。初始化腳本建立唯讀的 `takbind`、不到期的服務帳號密碼政策，並收緊 ACL。

### D1、D2：非 root 與唯讀憑證

- `slapd` 的行程 UID 是 100（`openldap`）。bootstrap 的九個步驟都成功，第一次啟動後 `636` 就可用。
- entrypoint 對憑證目錄的 `chown` 與 `chmod` 都失敗（唯讀檔案系統），啟動沒有中斷。
- 在 Windows Docker Desktop 上，掛載進去的金鑰對所有使用者可讀，所以非 root 的 `slapd` 讀得到。**Linux 主機上金鑰的擁有者與權限要另外確認，這次沒有測。**

### D3：服務帳號的密碼政策

為 `takbind` 指定 `pwdMaxAge: 0` 的政策後，它沒有 `pwdChangedTime`。把預設政策的 `pwdMaxAge` 暫時改成 20 秒：

| 帳號 | 結果 |
| --- | --- |
| 一般使用者 | `Invalid credentials (49); Password expired` |
| `takbind` | 繫結成功 |

改回原值後一般使用者恢復正常。

### D4：收緊後的 ACL

| 操作 | 結果 |
| --- | --- |
| 匿名查詢 base DN | `No such object (32)`，沒有回傳條目 |
| 匿名查詢 root DSE（健康檢查用） | 成功 |
| `takbind` 經 `ldaps://` 查使用者與 `memberOf` | 成功 |
| `takbind` 讀取密碼雜湊 | 只讀得到自己的 |
| `takbind` 寫入 | `Insufficient access (50)` |
| 一般使用者查詢其他使用者 | 沒有回傳條目 |

### D5、D6：TAK 端的信任

| 信任憑證庫內容 | TAK 啟動 | 在目錄內的使用者 | 不在目錄內的使用者 |
| --- | --- | --- | --- |
| 只有根 CA | 正常 | `tak_ALPHA` | 檔案內的群組 |
| 不相關的 CA | 正常，健康檢查通過 | 檔案內的群組 | 檔案內的群組 |

LDAP 伺服器送出兩張憑證（伺服器與中繼 CA），只用根 CA 驗證成功。

信任憑證庫錯誤時，TAK 的訊息紀錄與 API 紀錄裡沒有找到對應的 TLS 錯誤（只查了預設紀錄等級下的最近數千行）。行為與目錄斷線相同，從外部看不出設定有錯。

### D7、D8：稽核紀錄與還原

- 稽核紀錄掛在獨立的 volume。強制重建容器後，`auditlog.ldif` 的筆數不變，bootstrap 沒有重跑。
- 以 `slapcat -n 0` 與 `slapcat -n 1` 匯出設定與資料。移除設定與資料兩個 volume 後還原，使用者的 `memberOf`、服務帳號的密碼政策與 ACL 的雜湊都和還原前相同，`takbind` 可以繫結。

還原時要注意：

- 新的資料 volume 掛到 `/var/lib/ldap` 時，Docker 會把映像內的預設資料庫複製進去。它的 `dc=nodomain` 條目也會出現在匯出檔內，還原時要加 `slapadd -c` 略過。
- 新的設定 volume 要先掛到映像內不存在的路徑再 `slapadd -n 0`；直接掛到 `/etc/ldap/slapd.d` 會先被映像的預設設定填滿。
- 還原後要把兩個目錄的擁有者改回 `openldap`，並建立 `.bootstrap_completed`，否則 entrypoint 會重跑 bootstrap。

## 批次 E：管理介面與帳號密碼登入

實驗期間在 TAK 加上 `8446` 連接器（`clientAuth="false"`）、`8090` 輸入埠（`auth="ldap"`）與 `adminGroup="tak_ADMIN"`。

### E1：管理介面需要的權限

| 服務帳號 | `isLdapTakComplient` | 讀取使用者與群組 |
| --- | --- | --- |
| 唯讀的 `takbind` | `false` | 可用 |
| 可寫入的帳號 | `true` | 可用 |

反組譯確認這項檢查是實際建立一筆測試使用者再刪除，失敗時紀錄會寫出「write-compliance check failed」。所以管理介面一定要可寫入的服務帳號。

### E2：管理 API 的寫入功能

以 `adminGroup` 成員的帳號密碼登入後呼叫 `/Marti/api/ldap-user-management/`：

| 操作 | 結果 |
| --- | --- |
| 建立使用者 | HTTP 201；目錄內的物件類別是 `inetOrgPerson` 系列 |
| 把使用者加入不存在的群組 | HTTP 204；群組被自動建立 |
| 把使用者加入既有群組 | HTTP 204；`memberOf` 讀回一致 |
| 鎖定 | HTTP 204；目錄內出現永久鎖定的 `pwdAccountLockedTime`，登入被拒絕 |
| 解鎖 | HTTP 204；可以登入 |
| 移除成員、刪除群組、刪除使用者 | 都是 HTTP 204 |

沒有測的部分：群組異動套用到連線的時間、批次匯入、編輯使用者。建立時送出的呼號、角色與顏色沒有寫進目錄，原因是預設的 `userObjectClasses` 不含 TAK 的物件類別，沒有進一步測試。

### E3：誰能用管理 API

| 身分 | 讀取使用者清單 |
| --- | --- |
| 管理員憑證（`8443`） | HTTP 200 |
| 一般憑證（`8443`） | HTTP 403 |
| `adminGroup` 成員的帳號密碼（`8446`） | HTTP 200，`isAdmin` 為 `true` |
| 一般帳號密碼（`8446`） | HTTP 403 |

實測把 `adminGroup` 設成含前綴的完整群組名稱（`tak_ADMIN`）有效；不含前綴的寫法沒有試。**它的成員以帳號密碼登入就是 TAK 管理員，不需要憑證。**

### E4：可寫入服務帳號的風險範圍

實驗用的 ACL 讓可寫入帳號對整個目錄樹有寫入權。以它繫結：

| 操作 | 結果 |
| --- | --- |
| 修改唯讀服務帳號的條目 | 成功 |
| 修改目錄管理員的條目 | 成功 |
| 讀取所有帳號的密碼雜湊 | 成功 |
| 修改預設密碼政策 | 成功 |
| 修改 `cn=config`（含 ACL） | `Insufficient access (50)` |

它的密碼以明文存在 `CoreConfig.xml`。若採用管理介面，ACL 要把寫入範圍限制在 `ou=People` 與 `ou=Group`，並排除服務帳號與密碼政策；這次沒有測限制後管理介面是否仍可用。

### E5：`8446` 帳號密碼登入

`8446` 不接受 HTTP Basic，要先以 `POST /oauth/token`（`grant_type=password`）取得權杖。

| 情況 | 結果 |
| --- | --- |
| 正確密碼 | 取得權杖；可呼叫 API；群組與目錄一致 |
| 錯誤密碼、不存在的帳號 | HTTP 401 |
| 在目錄端鎖定後重新登入 | HTTP 401 |
| 鎖定前取得的權杖 | 鎖定後 20、80、140 秒仍然是 HTTP 200 |

權杖的效期是 7800 秒。鎖定帳號不會撤銷已簽發的權杖。

### E6：`auth="ldap"` 輸入埠

這種輸入埠仍然要求用戶端憑證，另外再要求第一筆訊息帶帳號密碼。

| 情況 | 結果 |
| --- | --- |
| 有效憑證加正確密碼 | 接受；群組來自目錄 |
| 有效憑證加錯誤密碼 | 伺服器關閉連線 |
| 甲的憑證加乙的帳號密碼 | 接受 |
| 鎖定後的新連線 | 伺服器關閉連線 |
| 鎖定時的既有連線 | 鎖定後 23 到 45 秒之間被伺服器中斷 |

對照組：同一個被鎖定的使用者以憑證連 `8089`，連線被接受並拿到 `tak_ALPHA`；以憑證呼叫 `8443` 是 HTTP 200。

### E7：密碼政策

只在目錄與 API 層觀察：

- 連續 5 次錯誤密碼後，目錄寫入 `pwdAccountLockedTime`，第 6 次以正確密碼登入也被拒絕。套件預設鎖定 900 秒。
- 管理 API 建立的使用者沒有 `pwdReset`，第一次登入不會被要求變更密碼。
- 套件預設密碼 30 天到期。到期後的提示在 ATAK 與 WebTAK 上如何呈現，沒有測。

## 對導入計畫的影響

- **撤銷流程可以加上「重建輸入埠」。**TAK 不能立刻重啟時，發布 CRL 後重建 `8089` 的輸入埠，可以先擋住新的串流連線。它不能取代重啟：`8443` 仍然接受該憑證，既有連線也不會中斷，要搭配隔離與踢除連線。
- **重建輸入埠會改寫 `CoreConfig.xml`。**若納入正式流程，bootstrap 產生設定的邏輯要能容忍展開後的屬性。
- **Compose 服務要加上 `command: ["-u", "openldap", "-g", "openldap"]`。**
- **LDAP 設定錯誤不會讓 TAK 啟動失敗。**啟用後一定要以訂閱 API 確認群組來自目錄，不能只看健康檢查。
- **是否採用 LDAP 管理介面要先決定 ACL。**它需要可寫入的服務帳號，而該帳號的密碼是明文。
- **`adminGroup` 是另一條取得管理員權限的路。**只要 `8446` 開著，群組成員不需要憑證就是管理員。
- **若開放帳號密碼登入，要調整密碼政策。**預設的失敗鎖定可以被用來鎖住別人。
- **目錄端的鎖定只對帳號密碼登入有效。**本專案目前只用憑證，停權仍然靠撤銷、隔離與重啟。

## 測試過程的問題

- 還原目錄資料時，原本要在容器內清空目錄再匯入，清除指令被工具的安全檢查擋下。改成把新的 volume 掛到不會被預先填入內容的路徑，結果寫在 D7、D8 一節。
- 第一次以 HTTP Basic 測 `8446` 全部得到登入頁（HTTP 403），改用權杖登入後才正確。
- D5 沒有用本專案的 CA 簽發憑證。那會在正式的 CA 資料庫留下一筆紀錄，應該由第 1 階段的實作來做。

## 未測試

- D9：bootstrap 開關切換；要等實作。
- 用本專案的中繼 CA 簽發 LDAP 憑證，並以 `truststore-root.jks` 驗證。
- Linux 主機上唯讀掛載的金鑰權限。
- 重建輸入埠時進行中的新連線、有大量連線時的行為，以及 `8443` 不重啟的重新載入方式。
- 鎖定後，既有權杖在 140 秒之後是否失效；WebTAK 的 WebSocket 是否中斷。
- 把可寫入帳號的 ACL 限縮後，管理介面是否仍判定為支援的容器。
- 管理介面的網頁本身、批次匯入、編輯使用者、群組異動的生效時間。
- ATAK 與 WebTAK 對密碼到期、鎖定的畫面提示。
- 批次 F（實體裝置）。
