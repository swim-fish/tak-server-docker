# 2026-11-14 撤銷時機、隔離群組與無群組憑證

## 結論

1. **撤銷憑證要等 TAK Server 重啟才生效。**在 CA 撤銷並發布 CRL 之後、TAK 重啟之前，既有連線繼續運作，用已撤銷憑證建立的**新連線也被接受**。檔案驗證與 LDAP 兩種模式的結果相同。
2. **LDAP 不能拒絕憑證連線。**已撤銷的憑證在 TAK 重啟前照樣拿到 LDAP 群組。
3. **TAK 不能立刻重啟時，把使用者移到只有他自己的隔離群組是有效的減災手段。**不需重啟：檔案模式 3 秒內、LDAP 模式 14 秒內套用到既有連線。隔離後他與原本的隊友互相收不到資料，在 `8443` 也看不到原群組的任務與連線清單。
4. **隔離必須同時改目錄與檔案兩邊的群組。**只改目錄時，目錄一斷線，TAK 退回檔案內的舊群組，隔離就失效。
5. **無群組的憑證不會被拒絕，而是進入 `__ANON__`（IN＋OUT）。**檔案模式與 LDAP 模式都一樣。它不是管理員，只看得到屬於 `__ANON__` 的資料。
6. **TAK 內建的即時撤銷不適用於本專案。**TAK 的憑證資料表是空的；外部 CA 簽發的憑證不在其中。

> 後續：[補測批次 A、B、C](2026-11-14-openldap-batch-abc.md)補測了本紀錄「未測試」的前三項，並補上一項限制：隔離會立刻停止位置等事件，但隔離前訂閱的任務仍會推送變更通知，要另外刪除任務訂閱。

本紀錄是同一天的數輪實驗，接續 [OpenLDAP 導入第 0 階段](2026-11-14-openldap-phase0.md)。所有測試憑證都已撤銷，實驗容器與測試任務都已移除，`runtime/tak/CoreConfig.xml` 的 SHA-256 與修改前相同。

## 測試環境

- TAK Server `5.8-RELEASE-84`（hardened），Windows Docker Desktop。實驗期間主機沒有 `.env` 的 `TAK_BIND_IP` 位址，`tak-server` 以 `127.0.0.1` 發布 `8089`／`8443`。
- LDAP 模式：官方 `takserver-ldap-5.8-RELEASE-92` 容器、唯讀服務帳號、`ldaps://`、`updateinterval="60"`，設定同第 0 階段。
- 測試憑證：每輪以憑證工作佇列簽發一日效期憑證，每輪使用新的 CN（工作佇列不允許重用已登錄的 CN）。
- 模擬用戶端：Python TLS CoT 用戶端，在 `tak-edge` 網路內的容器執行，每 2 秒送一筆 SA 事件並記錄收到的 UID。
- Android 模擬機：Android 16、ATAK 5.7.0.15（SDK 版），只用在案例 1。模擬機上的操作由 subagent 執行並判讀。
- 群組讀取：以管理員憑證呼叫 `GET /Marti/api/subscriptions/all`。API 權限測試則以各測試憑證直接呼叫 `8443`。

本紀錄不含密碼、實際位址、憑證序號或裝置識別資訊。

## 案例 1：連線中撤銷憑證

### 做法

專案的撤銷流程（憑證控制台、憑證工作佇列的 `revoke`）在發布 CRL 後一定會重啟 TAK，連線必然中斷，看不出既有連線的去向。本案例改用 `scripts/revoke_tak_certificate.py`：它在 CA 撤銷並發布 CRL，**不重啟 TAK**。撤銷後確認兩張憑證的序號都在掛載給 TAK 的 CRL 檔內。

LDAP 模式的三個身分都在 `tak_ALPHA`：模擬機、一個長時間連線的模擬用戶端、一個不撤銷的觀察者。檔案模式另以一張憑證做對照。

### LDAP 模式結果

| 時間點 | 既有連線 | 用已撤銷憑證建立的新連線 |
| --- | --- | --- |
| 撤銷並發布 CRL，TAK 未重啟 | 模擬機與模擬用戶端都維持連線並保有 `tak_ALPHA`；2 分鐘後觀察者仍收到兩者的事件 | 模擬用戶端：接受，並拿到 `tak_ALPHA` |
| 強制關閉並重開模擬機的 ATAK，TAK 仍未重啟 | — | 模擬機：17 秒後重新連上，拿到 `tak_ALPHA`，觀察者收到它的事件 |
| 重啟 TAK | 全部中斷 | 模擬用戶端：`SSLV3_ALERT_CERTIFICATE_REVOKED`。模擬機：約每 16 秒重試一次，每次都被拒絕 |

模擬機被拒絕時，ATAK 的紀錄先出現連線建立，50–90 毫秒後收到錯誤；`8443` 回的是 `CERTIFICATE_UNKNOWN`。ATAK 的紀錄沒有明確的 revoked 字樣，判定依據是時間點與模擬用戶端收到的 alert。

### 檔案模式對照

| 時間點 | 既有連線 | 新連線 |
| --- | --- | --- |
| 撤銷並發布 CRL，TAK 未重啟 | 90 秒後仍在訂閱清單內 | 接受，並與既有連線互相收到事件 |
| 重啟 TAK | — | `SSLV3_ALERT_CERTIFICATE_REVOKED` |

兩種模式的行為相同，所以這不是 LDAP 造成的。推論原因是 TAK 只在啟動時載入 `<crl>` 指定的檔案；撤銷腳本本身也提示要重啟。

未重啟的狀態只觀察了約 5 分鐘。沒有測 TAK 會不會在更長時間後自行重新載入 CRL。

## 案例 2：以隔離群組減災

### 檔案模式（LDAP 關閉）

目標使用者與隊友都在 `p7-alpha`，各有一條既有連線。以管理 API（`PUT /Marti/api/user-management/api/update-groups`）把目標使用者的群組改成 `p7-quar-bad`，不重啟 TAK。

| 觀察 | 隔離前 | 隔離後 |
| --- | --- | --- |
| 目標使用者既有連線的群組 | `p7-alpha` | 3 秒內變成 `p7-quar-bad` |
| 隊友收到目標使用者的事件 | 是 | 否 |
| 目標使用者收到隊友的事件 | 是 | 否 |
| 目標使用者在 `8443` 看到的任務 | `p7-alpha` 的測試任務 | 沒有 |
| 目標使用者在 `8443` 看到的連線與聯絡人 | 自己與隊友 | 只有自己 |

### LDAP 模式

目標使用者與隊友都在 `tak_ALPHA`。在目錄內建立 `tak_QUAR_bad`（成員只有目標使用者），並把他從 `tak_ALPHA` 移除。

| 觀察 | 結果 |
| --- | --- |
| 既有連線換到 `tak_QUAR_bad` | 14 秒後 |
| 隊友與目標使用者互相收到事件 | 都收不到 |
| 目標使用者在 `8443` 看到的連線與聯絡人 | 只有自己 |

### LDAP 模式下目錄斷線

這一輪目標使用者在檔案內的群組仍是原本的 `p6-alpha`（當輪的管理 API 呼叫失敗，見「測試過程的問題」）。

| 時間點 | 目標使用者的群組 | 與隊友互相可見 |
| --- | --- | --- |
| 停止 LDAP 容器後約 42 秒 | 退回檔案內的 `p6-alpha` | 是，隔離失效 |
| 重新啟動 LDAP 容器後約 53 秒 | 回到 `tak_QUAR_bad` | 否 |

這證明只改目錄不夠。檔案內的群組也要改成隔離群組；檔案模式的結果顯示這個修改同樣不需重啟。「目錄與檔案都改之後，目錄斷線仍然隔離」是由這兩項結果推得，沒有在同一輪直接驗證。

### 其他不重啟的手段

| 手段 | 結果 |
| --- | --- |
| TAK 內建的 Client Certificates 撤銷（`x509checkRevocation="true"`） | 不適用。`GET /Marti/api/certadmin/cert` 回傳 0 筆；外部 CA 簽發的憑證不在 TAK 的憑證資料表內，無從撤銷 |
| 刪除訂閱（`DELETE /Marti/api/subscriptions/delete/{uid}`） | 以 CoT 事件的 UID 呼叫得到 HTTP 400，連線沒有中斷。正確的識別碼沒有查明。即使能踢掉連線，CRL 未重新載入前對方仍可重連 |

## 案例 3：無群組的憑證

| 模式 | 條件 | TAK 分配的群組 |
| --- | --- | --- |
| 檔案 | 以管理 API 把檔案內的群組清空 | `__ANON__` IN＋OUT |
| LDAP | 帳號在目錄內，只屬於非 `tak_` 前綴的群組；檔案內另有群組 | `__ANON__` IN＋OUT，檔案內的群組被忽略 |
| LDAP | 帳號不在目錄內，檔案內有群組 | 檔案內的群組 |
| LDAP，目錄斷線 | 上述兩種帳號 | 都退回檔案內的群組 |

以 `__ANON__` 身分呼叫 `8443`：

| 項目 | 結果 |
| --- | --- |
| 是否管理員（`/Marti/api/util/isAdmin`） | HTTP 403 |
| 自己的群組（`/Marti/api/groups/all`） | `__ANON__` |
| 看得到的任務 | 只有屬於 `__ANON__` 的任務；看不到其他群組的任務 |
| 建立任務 | 可以；未指定群組時歸到建立者自己的群組 |
| `/Marti/api/subscriptions/all`、`/Marti/api/contacts/all` | HTTP 200，但只列出與自己同群組的連線 |

非管理員憑證呼叫 `/Marti/api/subscriptions/all` 會得到 HTTP 200，內容只限同群組的連線，沒有觀察到跨群組的資訊。

測試時 `__ANON__` 內只有一個使用者，所以「兩個無群組使用者互相可見」沒有直接測到；依群組規則推論會互相可見。

## 對維運的影響

- **撤銷之後一定要重啟 TAK，撤銷才算完成。**憑證控制台與工作佇列的撤銷流程已經包含重啟；單獨執行 `revoke_tak_certificate.py` 或 `refresh_tak_crls.py` 時不會。
- **TAK 不能立刻重啟時，先隔離、再撤銷、之後補重啟：**
  1. 檔案內的群組改成只有該使用者的隔離群組。
  2. 使用 LDAP 時，目錄內也移到只有他的隔離群組（名稱要符合 `groupprefix`），並從其他 `tak_` 群組移除。
  3. 以訂閱 API 確認他的群組已經改變。
  4. 照常撤銷憑證；等可以重啟時重啟 TAK。
- **不要只把群組移光。**那會讓他進入 `__ANON__`，和其他無群組的使用者互相可見。
- **隔離不是停權。**他仍然連得上 `8089` 與 `8443`，已經收到的資料也還在裝置上。隔離生效前有數秒到 2 分鐘的空窗。
- **管理 API 用戶端依賴 `TAK_BIND_IP`。**`scripts/tak_api_client.py` 固定連 `.env` 的綁定位址；主機沒有該位址時，控制台的群組修改會逾時。

## 測試過程的問題

- 憑證工作佇列要求至少一個群組，不能用它把群組清空；無群組的檔案狀態要用管理 API 設定。
- 前兩輪的管理 API 呼叫全部逾時，原因是上一項的 `TAK_BIND_IP`。受影響的步驟在最後一輪改為直接連 loopback 後重做。
- 模擬機的 ATAK 會對一日效期的憑證反覆顯示「憑證即將到期」對話框，遮住部分截圖；判定以伺服器端的訂閱群組與用戶端收到的事件為準。
- 各輪的模擬用戶端都收到少數來源不明的 UID，各自只出現在單一群組內，沒有查明來源。

## 未測試

- 目錄與檔案都設成隔離群組後，目錄斷線時的行為（由兩項結果推得）。
- 兩個以上無群組使用者之間的可見度。
- TAK 長時間不重啟時是否會自行重新載入 CRL。
- 撤銷案例在實體 Android 裝置上的行為；隔離與無群組案例只用模擬用戶端與 API。
- `8443` 上的資料包、裝置設定檔與聯邦在隔離或 `__ANON__` 狀態下的範圍；測試環境沒有相關資料。
- 帳號密碼登入（輸入埠 `auth="ldap"`、`8446`）搭配目錄端鎖帳號。
