### 本機匯入 callback 路徑

同版本 SDK `MissionPackageReceiver.fileUpdateCallback` 的 bytecode 顯示，ADD 分支呼叫 `new ExtractMissionPackageTask(file, this, null)`。已保存 `MissionPackageReceiver.javap.txt`；原有 `ExtractMissionPackageTask.javap.txt` 顯示 `onPostExecute` 處理匯入／保留套件、更新清單，且僅在 callback 非 null 時呼叫它，沒有讀取或傳送 Manifest 的 `onReceiveAction`。

參考原始碼中，讀取 `onReceiveAction` 並以 `AtakBroadcast` 傳送的程式位於收到／下載資料包的完成路徑。結合實機 `fileUpdateCallback ADD` 日誌，目前證據支持：**本次一般本機匯入可解壓縮任務資料，但沒有走 Vx 原生分享所依賴的接收後通知流程。** SDK 與參考原始碼不能取代裝置 UI 的任務建立驗收；也不應宣稱所有網路接收入口皆已驗證。

後續應先驗證 Vx 支援的原生任務載入入口或資料包接收流程，而不是僅換 UUID 或重新安裝 ATAK。若採 TAK Server 傳送，需另外確認授權與接收對象，且不能把包含裝置私鑰的整合包當作公開任務分享包。

驗收結論：此版本與本次套件經 ATAK 一般 Import → Local SD 匯入，能完成 TAK 設定與連線，但不能據此完成 Vx mission／channel／server 自動建立。這是本次入口的實測限制，不等同於 Vx 原生任務分享或其他接收入口完全不支援。

## 裝置 Vx APK 的接收流程核對

直接分析本次裝置的 `vx-base.apk`，以下為靜態 bytecode 證據，不等同於接收端實測成功。

1. `com.atakmap.android.gbr.vx.sharing.MissionSharingManager` 繼承 `BroadcastReceiver`。建構時透過 `AtakBroadcast` 註冊 `com.atakmap.android.gbr.multicastvoice.sharing.downloaded`，與原生包及自製 DPK 完全一致。
2. `onReceive` 比對此 action，啟動 `MissionSharingManager$d` 協程。它要求 Intent extras 的 `MissionPackageManifest` 值為真正的 ATAK `MissionPackageManifest` 物件；缺少或型別不符時記錄 `MissionPackageManifest not found in intent extras` 並返回。不能用字串路徑取代該物件。
3. 呼叫 `manifest.getLocalFiles()`，取得解壓縮後檔案。`q(List)` 嘗試 legacy JSON，`p(List)` 嘗試 `Mission.parseFrom(byte[])`；兩者都會走訪清單中的檔案並處理解析例外，並非只靠副檔名選擇。若任一 Protobuf 任務可解析，優先使用 Protobuf；否則退回 legacy JSON。
4. Protobuf 分支透過 `p00.c()` 建立內部 Mission，呼叫任務插入 callback，再由 `p00.f(missionUUID, connections, channels)` 傳入 repository 處理連線及頻道。callback 註冊點是 `m10`，其函式參照保留 `insertMissionAndChannels` 名稱。這證明 APK 有建立任務／連線／頻道的接收邏輯；尚未驗證自製 Protobuf 已完整通過這段流程。
5. `MissionSharingManager$c` 與 `b10.p()` 是分享完成／失敗的通知 callback，並不是一般本機檔案匯入器。APK Manifest 沒有宣告任務檔案的 ACTION_VIEW 接收入口；本次追查的 sharing 類別也未發現向 ATAK 一般 Import 註冊任務解析器的程式。此結論限定於已檢查路徑，不宣稱不存在所有其他入口。

參考 ATAK `AtakBroadcast` 原始碼的 `registerReceiver`／`sendBroadcast` 使用 `LocalBroadcastManager`，和系統 broadcast 是不同通道。單獨 `adb shell am broadcast -a ...` 既不是此程序內通道，也不會自動建立帶有 local files 的 `MissionPackageManifest`，不能當作有效的任務匯入測試。

可辨識的接收日誌依序包括 `Received intent: action=`、`MissionPackageManifest found. Mission name:`、`Number of local files:`、`Found protobuf missions. Count:`、`Processing Proto Mission: uuid=`。本次保存的 Vx-only 匯入 log 未出現這些訊息。`Parsed incorrect JSON/proto` 需看是哪個檔案及後續是否有任務成功，因為兩種解析器都會嘗試清單內的檔案，不能只看到單一解析失敗就判定整包失敗。

後續候選方案：以 Vx-only 任務包驗證 ATAK 資料包的接收／下載完成路徑，或開發 ATAK 程序內的相容匯入橋接外掛。前者需驗證實際入口是否傳送 `onReceiveAction`；後者需要正確建立 Manifest 與本機檔案關聯，並非在 XML 多加一個參數即可完成。未修改 APK、未注入 broadcast、未對外分享套件。

### 實際步驟

1. 確認 ATAK 已透過既有套件取得 TAK 連線與 CA 信任，Vx 已載入。
2. 開啟 Tools → Data Packages，找到 **ATAK Local Voice Only Test**（2 items）。點該列 Send → Select Server → **Local TAK Server 5.8**，將 Vx-only 套件上傳到本機伺服器；沒有選取 Contact，也沒有上傳包含裝置私鑰的整合包。

4. Available Packages 選 **ATAK Local Voice Only Test** → Download。畫面 hash 與原始 Vx-only DPK 的 SHA-256 相同，下載大小為 1449 bytes。
5. 開啟 TAK Voice → Missions，確認出現 **vx-only-test**。
6. 開啟任務，出現 **Enter Password for takbox.local**。填入本機 `runtime/secrets/mumble_server_password` 的既有值並確認。密碼提示時機、密碼來源與已儲存密碼行為，見 [首次 Mumble 密碼輸入說明](../atak/vx-missions.md#輸入密碼)。

已存在同 UID 的本機資料包不妨礙本次從伺服器下載後觸發 callback。這只證明本次由「尚無 Vx 任務」到「新增 Vx 任務」成功，不代表既有 Vx 任務重複下載的去重／覆寫行為已驗證。

### 使用者操作順序

1. Tools → Data Packages → Download，選 `Local TAK Server 5.8`；必要時重新整理清單。
2. 下載 **ATAK Local Voice Dual Test**。
3. TAK Voice → Missions → **vx-dual-test**，確認 Channel Pool 同時有 `01-P1` 與 `02-A1`。
4. 先在 VS1 分別選取兩個頻道，驗證快速切換。
5. 再測 VS1 選 `01-P1`、VS2 選 `02-A1`；確認兩者是否能同時維持連線及頻道，並對照 Mumble session 與移動紀錄。
6. PTT 按鍵指派與雙向語音另外驗收，先不啟用 Channel Linking。

不要改用 Local SD 匯入作為 Vx 任務建立驗收。DPK 不指定 VS1／VS2，也不帶入 PTT1／PTT2 的實體按鍵指派。

### 雙頻道實測結果

使用者依上述操作步驟回報「測試 ok」。後續唯讀核對結果：

- Android 11:04:34.856：收到 `sharing.downloaded`；11:04:34.866 解析一筆 Protobuf Mission，名稱為 `vx-dual-test`。
- Android 11:04:47.665–47.669：`Joining channel: P1`、`Connection successful`。
- Android 11:04:50.416–51.516：`Joining channel: A1`、`Connection successful`。
- Mumble 記錄兩個不同 session 驗證成功，分別加入 `Primary[2]` 與 `Alternate[3]`。
- 即時 TLS ServerSync 的 UserState 查詢確認 session 5 位於 Primary／ID 2，session 6 位於 Alternate／ID 3；兩者同時存在。查詢沒有移動使用者或修改頻道。
- Windows 同時觀察到同一台平板連入 `40000/TCP` 的兩條 `ESTABLISHED` 連線。

結論：本次 ATAK／Vx 版本可從伺服器下載雙頻道 Mission，並以獨立 Mumble session 同時加入同一台伺服器的 Primary 與 Alternate，符合 VS1／VS2 雙頻道使用情境。即使 DPK 兩頻道共用一個 connection UUID，實際啟用時仍建立兩個伺服器 session。PTT 按鍵指派、雙向語音與 UDP 音訊品質沒有從上述紀錄驗證，不延伸列為通過。

時鐘注意：本輪 Android 與 Mumble 容器在換算 UTC+8 後仍約差 33 秒，不能只靠秒級時間對齊；本次另外以新任務 UUID、P1／A1 加入紀錄、伺服器即時 session 和雙 TCP 連線交叉核對。

## 更換 Mumble 密碼以重現提示畫面

使用者要求更換一般 Mumble server password，驗證已儲存舊密碼時的重新登入提示並補拍文件截圖。

- 已將原密碼備份至 Git 忽略的 `runtime/secrets/`，再以隨機新值更新 `runtime/secrets/mumble_server_password`。
- 僅重建 `mumble` 服務使 Docker secret 生效；使用原有資料 volume、頻道與 TLS 憑證。TAK 服務及 SuperUser 密碼未變更。
- 以驗證 CA／主機名稱的 TLS 控制連線檢查：舊密碼遭拒，Mumble Reject type 為 4（WrongServerPW）；新密碼收到 ServerSync，登入成功。沒有輸出密碼值。
- 使用者重新操作後回報沒有密碼提示。Mumble 記錄 Vx 兩個 session 驗證成功，分別加入 Primary／Alternate；Android 亦記錄 `Connection successful`。
- 唯讀 UserState 查詢確認：session 4 為 registered user ID 3、channel ID 2；session 3 為 registered user ID 2、channel ID 3。兩者均帶有用戶端憑證雜湊，文件不記錄實際雜湊或使用者名稱。
- 一般密碼的新舊值測試使用未註冊臨時帳號，不能用其拒絕結果推論已註冊 Vx 身分一定會被拒絕。

原因核對：Mumble v1.5.915 的 [ServerDB.cpp](https://github.com/mumble-voip/mumble/blob/v1.5.915/src/murmur/ServerDB.cpp#L1300-L1334) 支援以憑證雜湊匹配註冊身分；[Messages.cpp](https://github.com/mumble-voip/mumble/blob/v1.5.915/src/murmur/Messages.cpp#L192-L219) 僅對未識別為註冊使用者的連線（`id == -2`）檢查一般 server password。此次已確認 Vx 以註冊身分登入；憑證匹配符合觀察結果，但未擷取伺服器內部驗證分支，不能僅憑 UserState 排除註冊帳號密碼驗證。

結論：一般密碼輪替已生效，但不會撤銷既有註冊使用者的驗證資格，這次無法用此方式重現密碼提示。尚未取得提示畫面截圖，也未刪除註冊使用者或重設 ATAK。後續若要測試首次登入，應另用乾淨的測試身分／伺服器資料庫。

本機證據：`runtime/device-vx-2026-09-22/password-rotation-user-state.json`、`password-rotation-logcat.txt` 及 `password-prompt-ui.xml`，均由 Git 忽略。

目前有效的密碼以 `runtime/secrets/mumble_server_password` 為準。原密碼備份與操作資訊只保留在忽略的 runtime，不提交版控。本次重建容器中斷了原有 Mumble session；依賴一般 server password 的用戶端需更新密碼，已有可驗證註冊身分的用戶端可能直接重新登入。

### 取消 Vx 註冊身分以測試重新驗證
