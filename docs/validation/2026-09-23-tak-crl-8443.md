# TAK 8443 與 8089 憑證撤銷驗證（2026-09-23）

這是當時 8443 connector 設定 `crlFile` 的歷史實測；測試完成後已依要求移除此屬性。以下結果不代表目前 8443 的撤銷行為。

回復後的 `CoreConfig.xml` 通過 5.8 XSD 驗證，TAK Server 重啟後為 healthy。有效用戶端憑證在 8443 呼叫 `/Marti/api/version` 仍取得 HTTP 200；已撤銷的舊測試憑證在 8089 仍收到 `certificate revoked`。回復後沒有對 8443 的撤銷行為作有效的前後對照，不能依下方歷史測試推定目前的 8443 會檢查 CRL。

## 測試當時的設定

環境為 Windows Docker Compose、TAK Server 5.8 Hardened RELEASE-84。用戶端憑證由本專案中繼 CA 簽發；`runtime/tak/certs/intermediate-ca.crl.pem` 為發布給容器的 CRL。測試當時，`CoreConfig.xml` 的兩個位置都指向 `/opt/tak/certs/files/intermediate-ca.crl.pem`：

```xml
<network>
  <connector port="8443" _name="https" crlFile="/opt/tak/certs/files/intermediate-ca.crl.pem" />
</network>
<security>
  <tls>
    <crl _name="TAK Local Issuing CA" crlFile="/opt/tak/certs/files/intermediate-ca.crl.pem" />
  </tls>
</security>
```

上方只節錄測試當時的相關節點，並非目前的完整設定。測試當時的檔案通過隨 Hardened 5.8 提供的 `CoreConfig.xsd` 驗證；TAK Server 重啟後回復 healthy。

## 實測步驟與結果

1. 簽發七天效期、僅供測試的 client certificate，CN 為 `crl-8443-probe-20260923`，序號為 `1008`；用 `UserManager.jar certmod -g local-test` 註冊。
2. 撤銷前，測試憑證可連上 8089；在 8443 呼叫 `/Marti/api/version` 取得 HTTP 200。
3. 用 `scripts/revoke_tak_certificate.py` 撤銷測試憑證、發布新 CRL，重新啟動 `tak-server`，並等到 healthy。
4. 離線使用 OpenSSL 驗證 CRL，測試憑證回報 `error 23: certificate revoked`。撤銷後，新建的 8089 TLS 連線回傳 `certificate revoked`；8443 在 HTTP 請求完成前回傳 TLS alert `certificate unknown`。8443 的 alert 名稱較籠統，不能單靠字樣辨識撤銷原因；撤銷前同一張已註冊憑證可取 HTTP 200，撤銷後立即遭 TLS 拒絕，構成這次驗收的前後對照。
5. 未撤銷的 `atak-client` 憑證仍可在 8089 交握，並在 8443 取得 HTTP 200。測試結束後已從 TAK 使用者清單移除測試身分；CA 資料庫仍保留撤銷紀錄。

本次只驗證 8089／8443 的新 TLS 連線，不涵蓋已建立的 session、8446 或其他 connector。後續若加入其他需要用戶端憑證的 HTTPS connector，需逐一設定並驗證其 `crlFile`。
