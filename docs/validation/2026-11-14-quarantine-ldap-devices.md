# 2026-11-14 隔離流程：LDAP 模式與 Android 裝置

## 結論

1. **隔離流程的八個步驟在 LDAP 模式下都成立。**結果與檔案模式一致：只改檔案沒有作用；改目錄後生效；隔離後任務、檔案、檔案搜尋與聯絡人的範圍都只剩自己；踢除後重連仍在隔離群組。
2. **在模擬機與實體手機上重做，結果與模擬用戶端一致。**兩台裝置都分別當過被隔離的對象。
3. **被隔離的 ATAK 仍然收到已訂閱任務的變更通知，檔案模式與 LDAP 模式都是。**實體手機以 Data Sync 外掛訂閱任務後隔離，隔離生效 60 秒以上再由隊友新增內容，手機的紀錄當下出現任務變更通知。刪除任務訂閱後就收不到。
4. **通知會洩漏新檔案的名稱，但下載不到內容。**手機收到通知後嘗試下載，伺服器回 404；Data Sync 的任務紀錄仍寫出「User added <檔名>」，檔案數也跟著增加。
5. **聊天訊息在隔離期間雙向都送不到**，私訊與 All Chat Rooms 都是。傳送端沒有任何失敗提示，解除隔離後也不會補送。
6. **先撤銷、重建輸入埠，再踢除，對方就連不回來。**手機之後 130 秒內重試 9 次全部被拒絕，隊友的模擬機全程保持連線。
7. **只改目錄、沒改檔案時，目錄一斷線隔離就失效。**實體手機在目錄停止後 45 秒退回檔案內的原群組，隊友重新看得到它。補改檔案內的群組後 2 秒內恢復隔離。
8. **撤銷後重建 `8089` 輸入埠，在真實的 ATAK 上有效。**重建前，已撤銷的憑證重新啟動 ATAK 仍連得上；重建後被拒絕，其他裝置沒有斷線。
9. **真實的 ATAK 被踢除後 15 到 26 秒就自行重連**，重連後仍在隔離群組。
10. **不能用 ATAK 的 Contacts 畫面確認隔離已生效。**伺服器停止轉送後，雙方畫面上的對方仍維持綠點 3 分鐘以上。
11. **被拒絕時 ATAK 只顯示「IO error; reconnecting」**，約每 15 秒重試一次，沒有提到憑證已撤銷。
12. **目錄內的群組變更在 11 到 67 秒之間生效**（`updateinterval="60"`）。

本紀錄接續[補測批次 A、B、C](2026-11-14-openldap-batch-abc.md)與[補測 C2 與批次 D、E](2026-11-14-openldap-batch-cde.md)，驗證[隔離使用者](../tak-server/quarantine.md)的步驟。所有測試憑證都已撤銷，實驗容器、volume、映像、測試任務與測試檔案都已移除，兩台裝置上的測試連線與 `adb reverse` 都已移除，`runtime/tak/CoreConfig.xml` 的 SHA-256 與修改前相同。

## 測試環境

- TAK Server `5.8-RELEASE-84`（hardened），Windows Docker Desktop，`tak-server` 以 `127.0.0.1` 發布 `8089`／`8443`。
- LDAP：官方 `takserver-ldap-5.8-RELEASE-92` 容器、唯讀服務帳號、`ldaps://`、`updateinterval="60"`。
- 四輪測試：

| 輪次 | 被隔離的對象 | 隊友 | 重點 |
| --- | --- | --- | --- |
| 1 | 模擬用戶端 | 模擬用戶端 | LDAP 模式的完整流程 |
| 2 | Android 16 模擬機 | 實體 Android 手機、模擬用戶端 | 裝置上的完整流程 |
| 3 | 實體 Android 手機 | 模擬用戶端 | 手機當對象的完整流程；任務通知以串流收訊時間判定 |
| 4 | 實體 Android 手機 | 模擬機、模擬用戶端 | Data Sync 畫面、聊天、無群組、先重建再踢除 |

- 兩台裝置都是 ATAK 5.7 系列。手機經 `adb reverse` 連到主機的 `8089`。裝置用三日效期的測試憑證。
- 裝置上的操作與判讀由 subagent 執行；伺服器端的時間線、群組與關鍵的紀錄時間戳由主流程核對。

本紀錄不含密碼、實際位址、憑證序號、呼號或裝置識別資訊。

## 任務變更通知

### 以 Data Sync 外掛觀察（第 4 輪，實體手機）

手機的 `8443` 被 ATAK 自己的本機網頁伺服器占用，所以把 `adb reverse` 開在另一個埠，並暫時把 ATAK 的 Secure Server API port 改成那個埠，測完改回原值。任務由手機在 Data Sync 內訂閱。

| 時間點 | 手機的紀錄 | 手機的畫面 |
| --- | --- | --- |
| 檔案模式，隔離前（對照組） | 新增內容後 0.2 秒收到任務變更通知（`t-x-m-c`），下載成功 | 任務顯示 1 個項目，通知「Finished downloading」 |
| 檔案模式，隔離生效 70 秒以上 | 收到任務變更通知；下載得到 HTTP 404，重試約 1.5 分鐘 | 通知「Failed to download <檔名>」；任務的檔案數變成 2 並帶紅色標記；任務紀錄出現「User added <檔名>」 |
| 之後在 Data Sync 重新整理任務清單 | 清單回應裡已經沒有這個任務 | 對話框「Feed deleted」，詢問是否移除本機內容；之後任務從本機清單消失 |
| 檔案模式，刪除訂閱後 | 沒有通知 | 沒有變化 |
| 解除隔離 | 任務重新出現，要重新訂閱 | 重新訂閱後 3 個檔案都下載成功 |
| LDAP 模式，隔離前（對照組） | 收到通知 | — |
| LDAP 模式，隔離生效 80 秒以上 | 收到通知；下載 404 | 通知「Failed to download <檔名>」；任務紀錄出現「User added <檔名>」 |
| LDAP 模式，刪除訂閱後 | 沒有通知 | 沒有變化 |

結論：

- 這次直接在紀錄裡看到通知的類型，兩種模式都是。
- **被隔離的人看得到新增檔案的名稱與任務紀錄的條目，但拿不到檔案內容。**
- 隔離後他若重新整理任務清單，ATAK 會把任務當成已被刪除並提議清掉本機內容。在那之前，他先前下載的內容都還在裝置上。
- LDAP 模式的對照組下載也是 404：測試檔是在檔案模式上傳的，屬於檔案群組，切到 LDAP 模式後群組不符。所以 LDAP 模式只驗證到通知這一層。這也表示切換驗證模式時，既有檔案的群組不會跟著轉換。

### 以串流收訊時間判定（第 3 輪，實體手機）

第 3 輪手機沒有載入 Data Sync 外掛，訂閱以 API 建立，並以 ATAK 的紀錄判定：連續 15 秒沒有收到資料時它會記一行。沒有事件時這一行穩定地每 15.1 秒出現一次；中間收到資料，下一行就延後。

| 時間點 | 紀錄的間隔 | 判定 |
| --- | --- | --- |
| 基準（沒有任何任務變更） | 15.1 秒，連續三次 | 方法有效 |
| 檔案模式，隔離生效 65 秒後 | 23.5 秒 | 收到 |
| 檔案模式，刪除訂閱後 | 15.1 秒，連續三次 | 沒有收到 |
| LDAP 模式，隔離生效 90 秒後 | 24.5 秒 | 收到 |
| LDAP 模式，刪除訂閱後 | 15.1 秒，連續三次 | 沒有收到 |

結果與第 4 輪一致。

### 刪除訂閱後清單沒有變

管理員刪除任務訂閱的呼叫回 HTTP 200，之後手機確實收不到通知；但 `GET /Marti/api/missions/<任務>/subscriptions` 回傳的筆數沒有減少。第 3、4 輪與兩種模式都一樣。原因沒有查明。**不能用這份清單確認訂閱已經刪除。**

### 模擬機（第 2 輪）

無法判定。模擬機的 ATAK 沒有安裝 Data Sync 外掛，當時也沒有用上述的時間判定法。

## 聊天訊息（第 4 輪）

手機與模擬機互傳 GeoChat，測試文字各不相同。

| 階段 | 手機→模擬機（私訊） | 模擬機→手機（私訊） | 手機→All Chat Rooms | 模擬機→All Chat Rooms |
| --- | --- | --- | --- | --- |
| 隔離前 | 送達 | 送達 | 送達 | 送達 |
| 手機被隔離 | 未送達 | 未送達 | 未送達 | 未送達 |
| 解除隔離後 | 送達 | 送達 | — | — |

- 隔離期間，傳送端的畫面只顯示自己送出的訊息，沒有失敗或等待中的提示。
- 隔離期間送出的訊息在解除隔離後沒有補送。

## 無群組憑證在 ATAK 上的表現（第 4 輪）

把手機在檔案內的群組清空：

- 訂閱清單顯示 `__ANON__` IN＋OUT；ATAK 維持連線，狀態為綠點。
- 之後才連上的模擬隊友沒有出現在手機的 Contacts。
- 模擬機的聯絡人仍顯示綠點，但那可能只是舊資料；手機是否完全收不到模擬機的位置，沒有確認。

## 先重建輸入埠再踢除（第 4 輪）

LDAP 模式，手機已在目錄與檔案兩邊隔離。依序：撤銷憑證（不重啟）、重建 `8089` 輸入埠、踢除手機的連線。

| 步驟 | 結果 |
| --- | --- |
| 重建輸入埠後 | 手機的既有連線仍在 |
| 踢除後 130 秒內 | 訂閱清單只剩模擬機；手機約每 15 秒重試，9 次都在連線建立後 0.1 秒內被中斷 |
| 手機畫面 | 紅點；通知「Error connecting to … (IO error; reconnecting)」 |
| 模擬機 | 全程保持連線 |

這是不重啟 TAK 的情況下，把人擋在 `8089` 之外的做法。`8443` 仍然接受他的憑證。

## 裝置上的觀察

### Contacts 畫面

隔離後伺服器已停止轉送（第三方用戶端只收得到未被隔離的裝置），但雙方畫面上的對方仍顯示綠點，100 秒與 3 分鐘後都是。隔離後才連上的第三方用戶端只出現在未被隔離的那一台，這一點與隔離一致。被隔離的裝置離線 4 分鐘以上後，對方畫面上它的聯絡人才變灰。

### 連線被拒絕時

重建輸入埠或重啟 TAK 之後，已撤銷憑證的 ATAK：

- 伺服器連線的狀態顯示「IO error; reconnecting」，通知列顯示無法連線，地圖上的 TAK 圖示為紅點。
- 紀錄裡是連線建立後立刻出現讀取錯誤，沒有 revoked 字樣。
- 約每 15 秒重試一次。

### 目錄斷線與恢復（第 3 輪，手機）

| 時間點 | 手機的群組 | 第三方看得到手機嗎 |
| --- | --- | --- |
| 停止 LDAP 容器後 22–39 秒 | 仍是目錄的隔離群組 | — |
| 45 秒起 | 檔案內的原群組 | 是，隔離失效 |
| 把檔案內的群組改成隔離群組後 2 秒 | 檔案內的隔離群組 | 否 |
| 啟動 LDAP 容器後 10 秒 | 回到目錄的隔離群組 | — |

第 1 輪另外觀察到：目錄斷線期間，沒被隔離的隊友也看不到屬於 LDAP 群組的任務，因為他退回了檔案群組。目錄恢復後就回來。

## 對隔離流程的影響

- **步驟 1（改檔案）與步驟 2（改目錄）缺一不可。**這次在實體手機上直接看到只做步驟 2 的後果。
- **步驟 3 以訂閱清單為準**，不要看 ATAK 的 Contacts。
- **步驟 4（刪除任務訂閱）是必要的**，檔案模式與 LDAP 模式都是。刪除後不要用任務的訂閱清單確認。
- **步驟 5 的預期**：ATAK 約 15 到 26 秒就會自己連回來。
- **步驟 7 之後，對方的既有連線不會中斷**，要等他重新連線時才被拒絕。先重建輸入埠再踢除，他就連不回來（已在實體手機上實測）。所以踢除要排在重建輸入埠之後。
- **刪除任務訂閱要盡早做。**每一筆殘留的通知都會讓他看到新增檔案的名稱。

## 測試過程的問題

- 第 2 輪的模擬機在第一次強制關閉並重開 ATAK 時，系統服務自行重啟並出現無回應對話框，恢復後重做，結果有效。
- 第 3 輪原本要用 Data Sync 外掛在手機上訂閱任務並觀察畫面，但外掛沒有載入，手機的 `8443` 也無法經 `adb reverse` 轉到 TAK，所以改成 API 訂閱與時間判定法。第 4 輪外掛已載入，並以改用另一個 API 埠的方式解決。
- 第 4 輪之前，手機的 ATAK 曾因兩個與版本不符的外掛反覆閃退，另有 5 次發生在移除網路介面時的原生層當機。外掛問題排除後第 4 輪沒有新的當機紀錄。原生層當機與前幾輪的測試有沒有關係，無法判定。
- 第 3 輪的測試檔案用完後，把一個只加過另一個任務的檔案加進 LDAP 模式的任務，作為刪除訂閱後的觸發事件。當時沒有其他訂閱者可以交叉確認伺服器確實送出了通知。
- 無法確認匯入的測試憑證是否還留在兩台裝置上 ATAK 的私有憑證儲存區。伺服器連線已刪除，憑證也都已撤銷。
- 部分截圖與紀錄含呼號、手機的區域網路位址與既有伺服器的主機名稱，沒有納入本儲存庫。

## 未測試

- 任務內的其他內容類型（地圖物件、任務紀錄的文字）在隔離後的通知是否洩漏更多內容；這次只測了檔案。
- 無群組的 ATAK 是否完全收不到具名群組成員的位置。
- 刪除任務訂閱後，清單筆數不變的原因；一次列出某位使用者所有任務訂閱的做法。
- 帳號密碼登入的 ATAK 在密碼到期、帳號鎖定時的提示；需要另外發布輸入埠。
- 裝置設定檔、聯邦在隔離狀態下的範圍。
