> 狀態：批次 A、B、C 已於 2026-11-14 執行，結果見[補測批次 A、B、C 紀錄](../validation/2026-11-14-openldap-batch-abc.md)；B4 不通過（隔離流程已加上刪除任務訂閱）。C2 與批次 D、E 也已執行，結果見[補測 C2 與批次 D、E 紀錄](../validation/2026-11-14-openldap-batch-cde.md)；D9 要等實作，其餘遺留項目列在下方「已執行批次的遺留項目」。隔離流程另以 LDAP 模式與 Android 裝置重做，結果見[隔離流程：LDAP 模式與 Android 裝置](../validation/2026-11-14-quarantine-ldap-devices.md)，涵蓋 F2、F3、F4，以及 LDAP 模式下的 B3、B4、C3、C4；F1 的人員調動與 F5 尚未以實體裝置重做。本計畫補足 [OpenLDAP 導入第 0 階段](../validation/2026-11-14-openldap-phase0.md)與[撤銷時機、隔離群組與無群組憑證](../validation/2026-11-14-revocation-quarantine-groupless.md)兩份紀錄列為「未測試」的項目。導入設計見 [OpenLDAP 導入計畫](openldap.md)。

## 範圍與順序

測試分成六批。前三批不需要改動專案的程式，可以用拋棄式容器直接做；第四批要先有第 1 階段的實作；第五、六批需要額外的環境或設備。

| 批次 | 主題 | 前置條件 | TAK 重啟次數 | 預估時間 |
| --- | --- | --- | --- | --- |
| A | 隔離與目錄斷線的組合 | 無 | 3 | 20 分鐘 |
| B | `__ANON__` 與隔離狀態的資料範圍 | 無 | 2 | 25 分鐘 |
| C | CRL 重新載入與強制斷線 | 無 | 2 | 50 分鐘（含等待） |
| D | 官方套件的調整與本專案 PKI | 第 1 階段的 Compose 服務與初始化腳本 | 2 | 40 分鐘 |
| E | LDAP 管理介面與帳號密碼登入 | 批次 D；`8446` 要另外開啟 | 3 | 60 分鐘 |
| F | 實體裝置與 ATAK 畫面 | 主機回到可發布通訊埠的網路；一台 Android 裝置 | 2 | 40 分鐘 |

建議順序是 A → B → C，這三批的結果會決定導入計畫第 6 節「停權與隔離」是否需要修改。D 隨第 1 階段實作進行，E 隨第 2 階段，F 在第 1 階段完成後做。

## 執行前要先修正的工具問題

第 0 階段的實驗有幾次因為工具問題重做。補測前先處理：

| 問題 | 處理方式 |
| --- | --- |
| 憑證工作佇列不允許重用已登錄的 CN | 每一輪用新的前綴產生 CN，腳本以參數接收前綴 |
| 套件建置失敗後腳本仍繼續部署 | 每個階段結束時檢查產物，失敗就中止 |
| 管理 API 用戶端固定連 `TAK_BIND_IP`，主機沒有該位址時逾時 | 測試用的輔助程式直接連 loopback；不修改專案的 `tak_api_client.py` |
| 簽發憑證後 TAK 會重啟，緊接著的 API 呼叫可能失敗 | 等 `tak-server` 回到 healthy 後再呼叫 |
| 紀錄檔在用戶端還在執行時被原地改寫，內容遺失 | 等所有用戶端結束後才整理紀錄，並寫到新檔 |
| Contacts 清單留著前幾輪的項目，本輪的項目被擠到畫面外 | 每輪開始前清除 ATAK 的聯絡人，截圖前捲到目標列 |
| 一日效期的憑證讓 ATAK 反覆顯示到期對話框 | 模擬機與實體裝置使用三日效期的憑證 |
| 模擬用戶端的紀錄沒有時間戳 | 每筆收到的 UID 記錄第一次與最後一次收到的時間 |

所有批次共用的規則：

- 每輪開始前備份 `runtime/tak/CoreConfig.xml` 並記錄 SHA-256；結束時還原並比對。
- LDAP 容器以另一個 Compose override 檔啟動，只接 `tak-backend`，不修改 `compose.yaml`。
- 測試憑證一日效期（裝置用三日），結束時全部撤銷；測試建立的任務與資料包全部刪除。
- 紀錄不含密碼、實際位址、憑證序號或裝置識別資訊。
- 模擬機與實體裝置上的操作交給 subagent：Sonnet 執行操作，Opus 判讀證據。

## 批次 A：隔離與目錄斷線的組合

回答導入計畫第 8 節的前兩項。

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| A1 | 目錄與檔案都設成隔離群組後，目錄斷線是否仍然隔離 | 目標使用者與隊友在 `tak_ALPHA`；檔案內也先設好各自的群組。依序：檔案改隔離群組、目錄移到隔離群組、停止 LDAP 容器 90 秒、重新啟動 | 四個時間點目標使用者與隊友都互相收不到事件；訂閱清單顯示的群組始終是隔離群組 |
| A2 | 帳號在目錄內、檔案裡完全沒有登錄時，目錄斷線的群組 | 簽發後從 `UserAuthenticationFile.xml` 移除該使用者（備份後修改並重啟），帳號留在目錄的 `tak_ALPHA`。停止 LDAP 容器，觀察既有連線與新連線 | 記錄實際群組。預期是 `__ANON__`；若是，確認它與另一個無群組使用者互相可見 |
| A3 | 平時就在檔案內登錄隔離群組的設計是否可行 | 三位使用者在目錄內同屬 `tak_ALPHA`，檔案內各自只有 `iso-<名稱>`。目錄正常、斷線、恢復三個階段各量一次 | 目錄正常時三人互相可見；斷線時三人互相不可見；恢復後 2 分鐘內回到互相可見 |

A2 的結果決定 A3 的設計是「建議」還是「必要」。

## 批次 B：`__ANON__` 與隔離狀態的資料範圍

回答「無群組或被隔離的使用者還拿得到什麼」。先以管理員憑證準備資料：`__ANON__`、`tak_ALPHA`、隔離群組各一個任務、一個資料包、一個裝置設定檔。

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| B1 | 兩個無群組使用者之間的可見度 | 兩張憑證在檔案內群組清空；同時連線 | 記錄雙方是否互相收到事件，以及 `8443` 的聯絡人清單是否列出對方 |
| B2 | `__ANON__` 使用者在 `8443` 的範圍 | 以該憑證列出並嘗試下載三個群組的任務、資料包、裝置設定檔 | 只拿得到屬於 `__ANON__` 的項目；其他群組的項目回 403 或不在清單內 |
| B3 | 被隔離的使用者在 `8443` 的範圍 | 使用者先在 `tak_ALPHA` 訂閱任務並下載資料包，再隔離。隔離後重新列出、下載、訂閱 | 隔離後拿不到 `tak_ALPHA` 的任何項目；既有的任務訂閱不再推送變更 |
| B4 | 隔離前已建立的任務訂閱是否殘留 | 接續 B3，由隊友在 `tak_ALPHA` 的任務新增內容 | 被隔離的連線沒有收到任務變更通知 |
| B5 | 建立任務時指定別的群組 | `__ANON__` 使用者建立任務並在參數指定 `tak_ALPHA` | 請求被拒絕，或任務沒有出現在 `tak_ALPHA` 成員的清單內 |

B3 與 B4 若不通過，隔離方案要加上「刪除該使用者的任務訂閱」這一步。

## 批次 C：CRL 重新載入與強制斷線

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| C1 | TAK 長時間不重啟時是否自行重新載入 CRL | 撤銷並發布 CRL 後不重啟。每 5 分鐘用已撤銷的憑證建立一次新連線，持續 40 分鐘 | 記錄第一次被拒絕的時間；40 分鐘內都被接受就記為「不會自行重新載入」 |
| C2 | 有沒有不重啟就重新載入 CRL 的方式 | 讀 `takserver.war` 內 CRL 相關類別的字串與設定指南；嘗試管理介面的 Manage Security 頁面儲存設定 | 找到並實測一種方式，或記為「沒有」 |
| C3 | 強制斷線 API 的正確識別碼 | 從 `GET /Marti/api/subscriptions/all` 的回應取出各個識別欄位，逐一用於 `DELETE /Marti/api/subscriptions/delete/{uid}` | 找到能中斷連線的欄位；記錄用戶端多久重連 |
| C4 | 隔離加強制斷線的效果 | 隔離後再強制斷線 | 重連後的新連線直接落在隔離群組，中間沒有回到原群組的時間點 |

C1 要等 40 分鐘，可以和批次 B 的資料準備同時進行，但兩者不能共用同一張被撤銷的憑證。

## 批次 D：官方套件的調整與本專案 PKI

隨導入計畫第 1 階段實作。每一項都是「套件預設有問題、調整後要確認沒有弄壞」。

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| D1 | `slapd` 不以 root 執行 | Compose 的 `command` 加上 `-u openldap -g openldap` | 容器內 `slapd` 的 UID 不是 0；bootstrap 完成；TAK 取得群組 |
| D2 | 憑證目錄唯讀掛載 | `./runtime/pki/ldap:/etc/ldap/certs:ro` | `636` 可連；entrypoint 的 `chown` 失敗不影響啟動 |
| D3 | 服務帳號不受密碼到期影響 | 為 `takbind` 指定不到期的密碼政策 | 讀回 `takbind` 的 `pwdPolicySubentry`；另以 `pwdMaxAge` 縮短到數分鐘的測試政策確認一般帳號會到期、`takbind` 不會 |
| D4 | 收緊 ACL 後 bootstrap 與健康檢查仍可用 | 套用導入計畫的 ACL | 匿名查詢 base DN 被拒絕；健康檢查（查 root DSE）仍成功 |
| D5 | 本專案 PKI 簽發的 LDAP 憑證 | 以中繼 CA 簽發 SAN 含 `tak-ldap` 的伺服器憑證；TAK 用 `truststore-root.jks` | TAK 經 `ldaps://` 取得群組；不需要額外的信任憑證庫 |
| D6 | 信任憑證庫沒有正確 CA 時的行為 | 暫時指向不含該 CA 的信任憑證庫 | 記錄 TAK 是退回檔案群組還是拒絕連線，以及紀錄內的錯誤訊息 |
| D7 | 稽核紀錄保存 | 掛載 `tak-ldap-audit` volume | 重建容器後 `auditlog.ldif` 仍在 |
| D8 | 目錄資料的備份與還原 | `slapcat` 匯出；清空 volume 後還原 | 還原後使用者的 `memberOf` 與還原前相同 |
| D9 | bootstrap 開關切換 | `TAK_AUTH_BACKEND` 在 `file` 與 `ldap` 之間切換各一次 | 切回 `file` 後 `CoreConfig.xml` 的 `<auth>` 與切換前相同 |

## 批次 E：LDAP 管理介面與帳號密碼登入

隨導入計畫第 2 階段與 `8446` 計畫進行。

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| E1 | 管理介面需要的權限 | 分別以唯讀的 `takbind` 與可寫入的服務帳號設定 TAK，呼叫 `isLdapTakComplient` | 找出讓檢查回 `true` 的最小權限 |
| E2 | 管理介面的寫入功能 | 在介面建立使用者、建立群組、調整成員、鎖定與解鎖 | 每個動作在目錄內讀回一致；群組異動在 2 分鐘內套用到連線 |
| E3 | 誰能用管理介面 | 設定 `adminGroup`；以管理員憑證與一般憑證各試一次 | 一般憑證無法存取 `/Marti/api/ldap-user-management/*` 的寫入端點 |
| E4 | 可寫入服務帳號的風險範圍 | 檢查該帳號能否修改自己與其他服務帳號的密碼、能否修改 ACL | 記錄實際權限；決定是否改由控制台用另一個帳號寫入 |
| E5 | 帳號密碼登入與鎖帳號 | 開啟 `8446`；以目錄帳號登入 WebTAK；在目錄端鎖定帳號 | 鎖定後新登入被拒絕；記錄既有工作階段多久失效 |
| E6 | 輸入埠 `auth="ldap"` | 另開一個 TLS 輸入埠並設 `auth="ldap"`；用模擬用戶端送驗證訊息 | 密碼正確才接受；鎖定帳號後新連線被拒絕 |
| E7 | 密碼政策對使用者的影響 | 以一般帳號經歷首次登入必須變更、連續失敗鎖定 | 記錄 ATAK 與 WebTAK 上的實際提示，判斷預設政策是否可用 |

E5 與 E6 是 LDAP 能真正拒絕連線的兩條路徑。本專案目前不採用，測試目的是確認它們可以當成日後的選項。

## 批次 F：實體裝置與 ATAK 畫面

| 編號 | 問題 | 做法 | 通過條件 |
| --- | --- | --- | --- |
| F1 | 實體裝置上的群組分配與調動 | 重做第 0 階段的模擬機情境：連線、目錄內調動、目錄斷線與恢復 | 訂閱群組與模擬機的結果一致；Contacts 清單在事件逾時後反映變化 |
| F2 | 隔離在 ATAK 上的表現 | 兩台裝置（或一台裝置加模擬機）同組；隔離其中一台 | 被隔離的一方在 2 分鐘內看不到對方的新位置；聊天訊息送不到對方 |

## 另行追查的項目

這些不屬於上面任何一批，也不阻擋導入：

- **來源不明的 UID。**每一輪的模擬用戶端都收到少數不是測試產生的 UID。做法：模擬用戶端把完整事件存檔，檢查事件類型與來源。若是 TAK 自己產生的事件，寫進紀錄後結案。
- **聯邦與 `__ANON__`、隔離群組。**本專案沒有啟用聯邦；等 [Federation Hub 串接](../tak-server/federation-hub.md)開始後再測。
- **大量使用者時的效能。**導入後以實際人數觀察 `updateinterval` 造成的目錄查詢量，再決定要不要測。
- **Active Directory 與巢狀群組。**本專案不規劃。
