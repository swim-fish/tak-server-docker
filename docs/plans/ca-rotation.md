# 中繼 CA 輪替與撤銷測試計畫

狀態：**本機測試已切換新中繼 CA，舊中繼 CA 已列入 Root CRL，且 TAK truststore 已移除舊 CA 的直接信任項目**。A 裝置使用舊憑證無法登入 ATAK，新憑證可登入 ATAK 並加入 Vx 四頻道；舊 Mumble 身分仍可登入 Vx。控制台清冊已能標示封存 CA 撤銷，但一鍵輪替與瀏覽器端到端操作仍待驗收。證據見[實際切換驗證](../validation/2026-09-25-ca-rotation-cutover.md)。本計畫適用目前的 Windows 本機測試機。日常輪替保留 Root CA，只更換簽發中繼 CA；Root CA 輪替另作遷移，不放在同一個按鈕。

## 現況與判定界線

目前 Root CA 預設有效 3650 天，中繼 CA 預設有效 1825 天。裝置、TAK、Mumble、MediaMTX 的葉憑證原先預設 730 天；控制台新增用戶端可選較短期限。介面顯示憑證實際 `notAfter` 與剩餘時間，不以預設天數推算。

同一 Root 簽出新的中繼 CA，**不會自動撤銷舊中繼 CA 或舊葉憑證**。舊中繼 CA 必須出現在 Root CRL，且相應驗證端實際檢查該 CRL，才能宣稱其鏈被撤銷。撤銷舊中繼 CA 不可逆；既有 DPK 與私鑰仍在裝置上，停止 QR 分享不會刪除已下載的副本。

本機 Root CA 資料庫的 `index.txt` 目前為空，雖然作用中的中繼 CA 憑證可由 Root 驗證。因此正式撤銷前，必須以**憑證指紋與序號**核對目標，並在 Root 資料庫中補登再撤銷；不能只依 CN 選取。隔離資料庫試驗結果見[前置驗證](../validation/2026-09-24-ca-rotation-preflight.md)。

## 實作順序

1. **備份與識別**：停止新的簽發作業，建立忽略版控的本機快照，驗證 SHA-256。記錄 Root／舊中繼 CA 指紋、序號、有效期，及現有憑證清冊。備份同時含私鑰、密碼與 DPK，限本機保存。PostgreSQL、Mumble 註冊資料庫與分享服務狀態須另作一致性備份；此快照不能代替它們。
2. **資料模型**：為每代中繼 CA 建立不可變 ID（建議中繼 CA 憑證 SHA-256 指紋），葉憑證以「簽發 CA ID＋序號」辨識。封存舊 CA 資料庫、葉憑證、CRL 與控制台 registry。現行清冊只讀作用中 CA 資料庫且 registry 只以序號為鍵，不能直接切換固定檔名，否則舊資料會消失或混淆。
3. **準備新鏈**：在隔離目錄由既有 Root 簽發新中繼 CA，建立新的 CA 資料庫與 CRL；重簽 TAK Server、管理員、Mumble、MediaMTX 葉憑證，並保留 `takbox.local` SAN。為測試裝置簽發新用戶端憑證，準備新的 `caCert.p12`、`clientCert.p12`、DPK 與短效 QR。先用 OpenSSL 驗證新舊鏈，確認新私鑰與憑證相符。
4. **切換服務**：切換 TAK keystore／truststore、Mumble 與 MediaMTX fullchain、控制台簽發設定及作用中 CA DB；更新憑證清冊。切換時逐項檢查容器健康、實際對外憑證與 SAN。先讓新 DPK 能登入，再撤銷舊中繼 CA，避免把「缺少新憑證」誤判為撤銷成功。
5. **撤銷舊中繼 CA**：在 Root CA 資料庫補登並撤銷經指紋核對的舊中繼 CA，產生 Root CRL，保留舊中繼 CRL 作為驗證歷史鏈之用。將 Root CRL 發布到所有需檢查舊鏈的入口，**移除 TAK truststore 對舊中繼 CA 的直接信任項目**，再重新載入服務。若舊中繼 CA 仍是直接信任錨，8089 可能在鏈到達 Root 前就接受舊憑證；本機實測確實如此。確認 Root CRL 含舊 CA 序號、有效期正確，且新中繼 CA 不在撤銷清單。
6. **停用舊交付**：停止舊 DPK／QR 分享；控制台顯示舊葉憑證的「簽發 CA 已撤銷」。這個狀態以 Root CA 資料庫／CRL 為依據，並另列各服務是否已驗證生效。原先單張葉憑證的 `revoked` 改標「憑證已撤銷」；只有輪替但未撤銷的 CA 標「已停用」。

控制台已加入「CA 替換」子頁，逐張重簽可保留 CN、顯示名稱、In／Out 群組及原到期日，並可調整或展延至送出後 5 分鐘至 730 天；已過期憑證不可選。啟動前須勾選兩個獨立核取方塊：理解既有憑證與 DPK 必須更換；理解服務及 ATAK／Vx 可能中斷且撤銷舊 CA 無法回復。背景工作會顯示階段與失敗狀態。本機控制台輪替已實際執行：第一輪因 TAK API 就緒時間超過原本的 20 秒而停在重簽後，使用原批次完成註冊，再發布 Root CRL 並移除舊 CA 直接信任錨；等待時間已改為 150 秒。舊鏈離線驗證與 8089 TLS 拒絕、新鏈 8089 與群組讀回通過。這證明本次**人工復原後**的結果，不等於無人值守的自動流程已通過；詳見[驗證紀錄](../validation/2026-09-25-wifi-env-ca-console.md)。

## 分開驗收：ATAK 與 Vx

| 階段 | ATAK 登入與 8443 | Vx 登入與頻道 |
| --- | --- | --- |
| 切換前 | 舊 DPK 的 8089 連線與 8443 Data Packages 可用；留截圖與服務紀錄。 | 舊任務能連 Mumble，逐一加入 Primary／Alternate／Medical／Emergency；留截圖與 Mumble 紀錄。 |
| 新鏈上線、舊 CA 未撤銷 | 新 DPK 可登入 8089，8443 能查到任務套件；舊 DPK 狀態另記。 | 新 TAK 設定載入 Vx 後，可登入四頻道；確認新 Mumble 伺服器鏈與 DNS SAN。舊 Vx 設定另記。 |
| Root CRL 發布後 | 舊 DPK 建立**新的** 8089 TLS 連線應遭拒；8443 用同一憑證測試並獨立記錄結果。新 DPK 兩入口仍可用。 | 舊 Vx 設定重新登入 Mumble 的結果**獨立記錄**；再用新 TAK 設定測試四頻道。Vx 使用的 Mumble 密碼／註冊身分不是 TAK 用戶端憑證，舊 Vx 若仍可登入，不能把它誤標為 CA 撤銷失敗，需另行輪替 Mumble 憑據或停用註冊身分。 |

另驗 Mumble 新憑證由 Vx 接受、MediaMTX RTSPS 仍可發布與讀取、ICU QR 仍可套用。Mumble 與 MediaMTX 不會因 TAK Root CRL 更新而自動拒絕原本的伺服器憑證；需檢查實際部署的新憑證。TAK 的 8443 connector 目前未設定 `crlFile`，不能預設它會拒絕舊中繼 CA 鏈；必須在測試中觀察並決定設定。

## 截圖與證據

測試時在同一時間點保存 ATAK 連線狀態、TAK Data Packages、Vx Mission／頻道、控制台憑證狀態與錯誤提示。原始圖放在忽略版控的 `runtime/validation/ca-rotation/`；文件只放遮蔽呼號、位置、裝置識別碼、私鑰、密碼及 QR token 的裁切圖。每張圖記錄測試步驟、裝置、日期時間、對應的伺服器 log 與預期／實際結果。OpenSSL、CRL、容器健康、8089／8443 握手結果以文字紀錄補足，不能只憑 Android 的 `IO error` 判斷撤銷原因。

## 中止與回復界線

新 CA 未能簽發、服務鏈不符或新 DPK 無法登入時，停止在撤銷舊中繼 CA 之前；可回復備份的作用中設定。**Root CRL 一旦發布舊 CA 撤銷狀態，就不以還原舊檔案作為正常回復**；改修復新鏈並重新簽發。若 8089、8443 或 Vx 仍接受舊憑據，標記該入口未達成停權驗收並保留 log，不宣稱全部舊憑證已失效。
